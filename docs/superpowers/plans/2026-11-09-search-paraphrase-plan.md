# 검색 개선: 표현이 다른 질문 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 사용자가 설명서와 다른 말로 물어도(예: "습기만 빼고 싶어요" ↔ 설명서 "제습 운전") 정답 조각을 찾게 한다. 정확도를 올리되, 질문 하나당 운영 비용과 응답 시간은 거의 늘리지 않는 방법을 먼저 찾는다.

**배경:** 1차 강사 피드백("뜻은 같지만 표현이 다른 질문에서 검색이 실패하는 문제를 개선"), 1차 오답 q12·q20, 근거 관련성 조사(d12-3: 설명서 용어로 옮기면 정답이 20위 → 1위). 결정기록 012·015·020·028, `docs/평가/v15-cr-investigation.md`

**Tech Stack:** Python, Neon(pgvector), OpenAI 임베딩(text-embedding-3-small), 기존 `app/retrieval/`, 작업 B의 검색 실험 도구, `evaluation/`, `measure/`

## 1. 설계

### 1-1. 평가 세트 (P 세트: 표현이 다른 질문)

- **출처:** 구글 폼으로 모은 사람들의 실제 문장(상황 카드 22개). 사용자 본인 문장 포함. 이름·개인정보는 받지 않음
- **정답 근거:** 카드마다 설명서 쪽·조각을 사람이 원문과 대조해 확정. **답이 있는 쪽을 모두 적는다**(2026-11-10 사용자 추가: 한 쪽만 적으면 다른 정답 쪽이 검색돼도 실패로 잡힌다. 1차 30문항 q22는 42·51쪽 모두 안내하지만 기대 근거가 42쪽뿐)
- **나누기:** **카드 단위로** 개발용(P-dev)과 확인용(P-test)으로 나눈다. 같은 카드의 문장들은 같은 쪽에만 들어간다(같은 상황의 다른 표현이 양쪽에 섞이면 확인용이 새어 나감). 모델별로 고르게, 정해진 난수 시드로 한 번만 나눈다
- **확인용 봉인:** P-test는 나눈 직후 파일 해시를 기록하고, **3단계 전까지 어떤 방법으로도 검색·채점하지 않는다**
- **회귀용:** 1차 30문항, 이어지는 질문 세트(13대화)

### 1-2. 후보 방법 (운영 비용이 낮은 순서)

| 이름 | 방법 | 질문당 추가 비용·시간 | 한 번만 드는 비용 |
| --- | --- | --- | --- |
| M0 | 지금 운영 검색 (기준) | 0 | 0 |
| M1 | **조각에 제목 붙여 임베딩**: 조각 앞에 "모델 · 문서 제목 · 쪽의 소제목"을 붙인 글로 다시 임베딩 | 0 | 다시 임베딩(1센트 미만) |
| M2 | **조각마다 "사용자가 물을 법한 질문" 미리 만들기**: AI가 조각마다 일상 말투 질문 3~5개를 만들어 함께 임베딩. 검색 때 조각 점수 = max(조각 유사도, 그 조각 질문들의 유사도) | 0 | 질문 생성 + 임베딩(실행 전 추정) |
| M3 | **용어 사전으로 질문 넓히기**: 설명서의 기능 이름마다 일상 표현 목록을 미리 만들어 두고(AI 생성 + 사람 검토), 질문에 일상 표현이 있으면 설명서 용어를 **덧붙여** 검색(사용자 말은 지우지 않음) | 문자열 비교만 | 사전 생성(실행 전 추정) |
| R1 | **넓게 찾고 다시 순위 매기기**: 상위 20개를 AI가 다시 골라 5개 | 질문마다 AI 호출 1번 + 시간 | 0 |

- M2·M3의 사전·질문은 **설명서만 보고** 만든다. P 세트 문장을 보여 주거나 참고하지 않는다(평가 세트에 맞춘 조정 방지)
- M1~M3은 서로 섞을 수 있다(조합은 2단계에서 한 번만)
- R1은 M1~M3 중 1단계 기준을 넘는 방법이 없을 때만 시험한다

### 1-3. 측정 깔때기

| 단계 | 대상 | 재는 것 | 비용 |
| --- | --- | --- | --- |
| 1단계 | M1·M2·M3 각각(+필요하면 R1), **P-dev와 1차 30문항** | 검색만: 정답 조각 5위 안 적중률, 평균 역순위 | 거의 0 |
| 2단계 | 1단계 통과 상위 1~2개(조합 1개 포함 가능), **P-dev** | 답변까지: 사람 판정 정답률, 질문당 비용, 같은 실행 안 응답 시간 | 몇 센트 |
| 3단계 | 최종 후보 1개 vs M0, **P-test + 30문항 + 이어지는 질문 세트** | 검색 적중률, 사람 판정, 환각, DeepEval(근거 관련성), 같은 실행 안 응답 시간, 질문당 비용 | 약 1달러 안팎 |

### 1-4. 판단 기준 (2026-11-09 사용자 확정, 이후 변경 금지)

**1단계 통과 (후보 고르기)**
- P-dev 적중률(5위 안)이 M0보다 **15%p 이상** 오름
- 1차 30문항 적중률이 M0보다 **1문항 넘게** 떨어지지 않음
- 통과한 것 중 P-dev 적중률이 가장 높은 것. 차이가 1문항 이내면 운영 비용·복잡도가 낮은 쪽

**2단계 통과**
- P-dev 사람 판정 정답률이 M0보다 **10%p 이상** 오름, 환각 0
- 질문당 운영 비용이 M0의 **1.5배 이하**, 같은 실행 안 응답 시간 증가 **0.5초 이하** (R1은 이 기준으로 판단)

**3단계 채택 (최종)**
1. P-test 적중률이 M0보다 **10%p 이상** 오르고, 사람 판정 정답률도 M0보다 높음, 환각 0
2. 1차 30문항: 사람 판정 27/30에서 **2문항 넘게** 떨어지지 않음, 환각 0
3. 이어지는 질문 세트: 정답 17/18에서 **1문항 넘게** 떨어지지 않음, 환각 0
4. 질문당 비용·응답 시간: 2단계 기준과 같음

**결과가 기준에 못 미치면:** 미채택으로 기록하고 운영은 M0 유지. 기준을 바꾸거나 같은 세트로 다시 고르지 않는다. 다른 방법을 시험하려면 새 확인용 세트를 만든다.

### 1-5. 지켜야 할 것

- **운영 표는 건드리지 않는다.** 실험 색인은 별도 표(예: `chunk_variants`)에 둔다. DB 구조 변경은 **실행 전에 사용자 확인**(CLAUDE.md 규칙)
- 운영 반영은 3단계 채택 뒤에만. 반영할 때는 적재 파이프라인(`python -m ingest`)도 같이 바꿔, 앞으로 추가할 모델도 같은 방식으로 들어가게 한다
- 비용: "검색 개선" 장부, 상한 4달러, 운영용 OpenAI 잔액 최소 1달러. 실행 전 예상 비용 기록 → `check_budget`
- 모든 실행은 `.settings.json`을 남기고, 운영 기본값과 다르면 경고(실험 색인을 쓰는 실행은 그 사실을 설정에 기록)
- 사람 판정이 최종 기준. DeepEval은 보조 지표(과대평가 경향 감안)

## 2. 작업 (Task)

**순서:** Task 3~6의 **만들기**(실험 색인, M1 제목, M2 질문 생성, M3 용어 사전)는 P 세트가 모이기 **전에** 먼저 한다. 방법을 평가 세트를 보기 전에 완성해 두면, 세트에 맞춘 조정이 원천적으로 막힌다. **측정**(1단계부터)은 Task 1·2가 끝난 뒤에만 한다.

### Task 1: P 세트 정리와 정답 근거 확정

**Files:** Create `evaluation/paraphrase.csv`, `evaluation/paraphrase_split.json`
- [ ] **Step 1:** 폼 응답 CSV(사용자가 제공, 이름·연락처 칸이 있으면 지운 상태)를 카드 번호와 문장으로 정리. 같은 문장 중복 제거, 동의 안 한 응답 제외, 개인정보가 섞인 문장은 가짜 값으로 바꾸거나 제외
- [ ] **Step 2:** 카드마다 기대 근거(모델·쪽·조각)를 초안으로 달고(**답이 있는 쪽은 모두**, 1-1), **채팅 Claude가 설명서 원본으로 대조한 표**를 받아 **사용자가 확정**. 설명서에 답이 없는 카드는 함정으로 표시
- [ ] **Step 3:** 카드 단위·모델별로 개발용/확인용을 나눈다(시드 고정). 확인용 파일의 해시를 `paraphrase_split.json`에 기록
- [ ] **Step 4:** 테스트: 같은 카드가 양쪽에 없음, 모든 행에 기대 근거 또는 함정 표시, 해시 일치
- [ ] **Step 5:** Commit → PR → 병합 직전 멈춤

### Task 2: 기준값 (M0, P-dev와 30문항)

- [ ] 작업 B의 도구로 M0의 P-dev·30문항 적중률과 평균 역순위를 잰다(임베딩 비용만). P-test는 재지 않는다
- [ ] P-dev 실패 문항을 "설명서 용어와 어긋남 / 다른 이유"로만 분류해 리포트에(원인 단정 금지)

### Task 3: 실험 색인 준비 (DB 구조 변경, 사용자 확인 필요)

- [ ] 별도 표 설계안(열, 인덱스, 지우는 방법)을 먼저 보고하고 **사용자 확인 후** 만든다
- [ ] 검색 함수에 `variant` 인자(기본값 = 운영)를 추가. 기본값이면 지금과 똑같이 동작함을 테스트로 고정

### Task 4: M1 (조각에 제목 붙이기)

- [ ] 조각마다 붙일 제목을 정하는 규칙(문서 제목, 쪽 소제목 추출 방법)을 테스트로 고정 → 실험 색인에 임베딩 → 1단계 측정

### Task 5: M2 (조각마다 질문 미리 만들기)

- [ ] 생성 프롬프트를 `docs/프롬프트.md`에 기록(설명서 조각만 입력, 일상 말투, 설명서 용어를 피한 질문과 쓴 질문을 섞기, 조각에 없는 내용은 묻지 않기)
- [ ] 조각 5개로 시험 생성 → 사용자가 질문 품질을 훑어봄 → 예상 비용 기록 → 전체 생성·임베딩 → 1단계 측정

### Task 6: M3 (용어 사전)

- [ ] 설명서에서 기능 이름 목록을 뽑고, 이름마다 일상 표현을 AI로 만든 뒤 **사용자가 검토**(지울 것·고칠 것)
- [ ] 질문 넓히기 함수(덧붙이기만, 사용자 말 유지)를 테스트로 고정 → 1단계 측정

**M3 규칙 (2026-11-10 사용자 확정, 측정 전, 이후 변경 금지)**
1. 이름 줄이기: 사용자가 쓰는 기능·코스·모드·관리 작업만 남기고, 부품 이름·화면 표시 이름·너무 일반적인 말(전원·설정·표시부 등)은 지운다. AI로 1차 분류한 뒤 남은 목록만 사용자가 검토한다.
2. 맞추는 방법: 표현의 핵심 단어(조사 제외, 두 글자 이상)가 질문에 모두 있으면 맞춘 것으로 본다. 맞으면 설명서 용어를 덧붙이기만 한다(사용자 말 유지).
3. 겹친 표현: 같은 표현이 기능 이름 2개 이하에 붙어 있으면 모두 덧붙이고, 3개 이상이면 그 표현은 지운다.

**M2 프롬프트 v2 (2026-11-10 사용자 요청):** 질문의 절반 이상은 기능 이름 없이 증상·하고 싶은 일로 묻는다. 조각 안에 답이 있는 질문만 만든다(숫자·온도·시간을 묻는 질문은 조각에 그 숫자가 있을 때만). 질문마다 답이 되는 조각 문장 한 줄을 함께 만들고, 답할 문장이 없으면 그 질문은 버린다(근거 문장은 임베딩하지 않음).

### Task 7: 1단계 판정과 2단계

- [ ] 1-4의 기준대로 1단계 판정표 작성. 통과가 없으면 R1을 시험하고 같은 기준으로 판정

### Task 8: 3단계 (확인용 봉인 해제)

- [ ] 1-4의 채택 기준 판정. 결론과 무관하게 결정기록(029)에 남긴다
