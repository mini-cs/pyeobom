# 2차 Task 11 ① "내 요청" — 첫 화면 요약 + 목록 화면 (짧은 설계)

- 날짜: 2026-11-27
- 상태: 확정(사용자 승인 2026-11-27)
- 관련: 2차 설계 `docs/superpowers/specs/2026-11-17-phase2-model-request-design.md` 3.2(목표 "내 요청" 카드)·3.6(밀리면 가장 먼저 뺌)·10-2(다른 계정으로 로그인하면 내 요청이 안 보임)·10-7(Supabase가 멈춰도 질문하기는 그대로), 2차 계획 `docs/superpowers/plans/2026-11-21-phase2-model-request-plan.md` Task 11, `supabase/schema.sql`(RLS "본인 요청만 읽기")
- 크기: 작은 기능 하나(화면 코드만, 서버·DB 구조 변경 없음). Task 11의 세 가지 중 첫째(순서는 사용자 결정 2026-11-27: 카드 → 실제 흐름 테스트 → 깨우기)

## 왜

- 요청한 사람이 메일을 기다리지 않고 첫 화면에서 자기 요청의 상태(대기·확인 중·추가됨·추가 어려움)를 본다(설계 3.2)
- 지금 화면에는 내 요청 목록이 없어서, "다른 계정으로 로그인하면 내 요청이 안 보임"(설계 10-2, RLS 시연)을 화면으로 보여 줄 곳이 없다. 다음 단계인 실제 흐름 테스트와 시연 영상이 이 화면을 쓴다

## 목표

1. 로그인했고 요청이 1건 이상이면 첫 화면에 요약 한 줄이 보이고, 누르면 내 요청 전부를 보는 화면이 열린다
2. 다른 계정으로 로그인하면 그 계정의 요청만 보인다(남의 요청은 0건)

## 하지 않을 것

- 서버 코드·DB 구조·RLS를 바꾸지 않는다. 질문·답변 코드(`app/ask/`·`app/retrieval/`·`app/answer/`)는 손대지 않는다(2차 계획 Global 1)
- 요청 고치기·지우기, 상태가 바뀌면 화면이 저절로 바뀌는 실시간 갱신, 서랍(☰)에 "내 요청" 넣기는 하지 않는다
- 요청자 이메일은 이 화면에 보이지 않는다(2차 계획 Global 2)

## 실패로 볼 것

- 다른 사람의 요청이 보인다
- 로그인하지 않은 방문자의 첫 화면이 지금보다 무거워진다(공개 설정 요청·supabase-js를 더 받는다)
- Supabase가 응답하지 않을 때 첫 화면·모델 고르기·질문하기가 막힌다
- 운영자가 적은 사유 글이 HTML로 해석된다

## 접근

- 고름: **A. 화면이 Supabase에서 바로 읽기 + 이 브라우저에 로그인 기록이 있을 때만**(사용자 결정 2026-11-27). 본인 것만 읽히는 일은 이미 있는 RLS "본인 요청만 읽기"가 맡는다. 서버 코드·비밀 값이 늘지 않는다
- 고르지 않음: B. 서버에 새 주소(`/api/my-requests`) — 서버 코드·테스트가 늘고, 서버가 관리자 키로 읽으면 RLS 시연이 흐려진다
- 고르지 않음: C. 첫 화면에서 항상 Supabase를 부르기 — 로그인하지 않은 방문자도 매번 공개 설정 요청과 supabase-js(약 220KB)를 받고, "처음 화면에서는 아무것도 부르지 않는다"(`public/js/auth.js`)가 깨진다
- 화면 방식은 시안 세 가지(가장 최근 1개 / 요약 + 목록 화면 / 전부 나열) 중 **요약 + 목록 화면**(사용자 결정 2026-11-27)

## 정한 것 (사용자 결정 2026-11-27, 시안 그림 기준)

1. 첫 화면: 최근 대화 위에 요약 한 줄. 제목 `내 요청 N건`, 아래 줄은 상태별 개수를 `추가됨 n · 확인 중 n · 대기 n · 추가 어려움 n` 순서로, 0인 상태는 적지 않는다. "추가됨 n"은 굵게. 오른쪽에 › 아이콘. 누르면 "내 요청" 화면
2. 로그인하지 않았거나 요청이 0건이면 첫 화면에 요약 줄이 없다
3. "내 요청" 화면(주소 `#requests`): 제목 `내 요청`, 요청 전부를 상태가 최근에 바뀐 순(`updated_at` 내림차순)으로
   - 한 줄: 제목 `<브랜드> <모델명>`(요청할 때 쓴 글 그대로), 아래 줄 `<가전> · <상태> · <바뀐 날>`(상태 굵게, 날짜는 지금 첫 화면 최근 대화와 같은 "11월 27일" 형식)
   - 추가됨: 셋째 줄 `눌러서 바로 질문하기`, 오른쪽 › 아이콘, 누르면 그 모델의 새 대화(`#chat/<model_id>`)
   - 추가 어려움: 셋째 줄 `사유: <운영자가 적은 사유>`
   - 대기·확인 중: 두 줄만, 누를 수 없음
   - 목록 아래 안내: `추가됨이나 추가 어려움으로 바뀌면 메일로도 알려 드려요.`(지금 화면의 안내 상자 모양)
4. 추가됨인데 그 모델이 이 배포의 모델 목록에 없으면 누를 수 없게 둔다(셋째 줄 없음)
5. 로그인하지 않고 `#requests`로 바로 들어오면 로그인 시트를 연다(지금 요청 화면과 같은 방식). 로그인하면 그 화면을 다시 그린다. 로그인했는데 0건이면 `아직 요청이 없어요`와 [시작하기](`#category`)
6. 첫 화면은 이 브라우저에 Supabase 로그인 기록(localStorage 키 `sb-<프로젝트>-auth-token`)이 있을 때만 Supabase를 부른다. Supabase가 응답하지 않거나 읽기가 실패하면 요약 줄만 안 보이고 나머지는 그대로
7. 서랍에는 넣지 않는다

## 채팅 Claude가 정한 것 (읽으며 고칠 수 있음)

1. 로그인 기록 확인: localStorage 키 중 `/^sb-.+-auth-token$/`에 맞는 것이 있는지만 본다(값은 읽지 않음). 키 형식은 저장소의 supabase-js 사본(`public/vendor/supabase.js` 2.119.2) 코드 `sb-${hostname 첫 마디}-auth-token`에서 확인했다. supabase-js를 올리면 다시 확인한다. localStorage를 못 쓰는 브라우저에서는 "기록 없음"으로 본다
2. 읽는 칸: `id, category, brand, model_text, status, model_id, reason, updated_at`(이메일·user_id는 읽지 않는다). 첫 화면과 "내 요청" 화면에 들어올 때마다 새로 읽는다(저장해 두지 않음)
3. 기록은 있는데 세션이 끝났으면(만료·로그아웃) 첫 화면 요약 줄은 없다. "내 요청" 화면에 있는 동안 로그아웃되면 첫 화면으로 간다(지금 요청 화면이 모델 화면으로 가는 것과 같은 방식)
4. 모양은 지금 최근 대화 카드(`.conv-card`·`.card-title`·`.card-meta`)와 안내 상자(`.notice`)를 다시 쓰고, 새 CSS는 `docs/design/디자인-가이드.md`의 변수만 쓴다. 상태는 글자(굵게)로 구분하고 색으로만 구분하지 않는다
5. 사유·브랜드·모델명은 글자로만 넣는다(`textContent`)
6. 화면 없이 시험할 수 있는 부분은 `public/js/request.js`의 순수 함수로 둔다(요약 개수·한 줄 모양·로그인 기록 확인). 화면 테스트는 `tests/web/test_ui_request.py`의 가짜 Supabase로(실제 Supabase 0번). 계획 Task 11의 테스트 이름 `test_my_requests_card_shows_status`를 쓴다
7. Task 11을 세 부분으로 나눠 하므로 PR도 나눈다. 이 부분은 브랜치 `feat/phase2-my-requests`, PR 하나(2차 계획 브랜치 전략은 Task 11 전체를 `feat/phase2-qa` 하나로 적었음 — 나머지 둘의 브랜치는 그때 정함)
