## 1. 한 줄 요약

내 가전 모델이 펴봄에 없으면 **로그인하고 요청**하고, 내가 설명서를 넣어 **모델이 추가되면 메일로 알림**을 받아 바로 질문하는 흐름을 만든다. 모델 추가는 **도구로 빠르고 안전하게** 하고, 그 시간을 전후로 잰다.

- 11/20 신청용 주제 한 줄 (제안): **"펴봄 — 내 가전 모델이 없으면 요청하고, 추가되면 바로 물어볼 수 있는 설명서 Q&A"**
- 형태: 개인 (사용자 결정, 팀이면 UI/UX 디자이너와 2인 → 16절)

## 2. 왜 하는가

1. 1차·1.5차의 펴봄은 모델 3개로 고정돼 있다. 내 모델이 없으면 펴봄을 쓸 수 없다.
2. 사전 설문(21명)에서 옵션 가전 원룸 사용자 6명 중 5명이 세탁기 설명서가 없거나 있는지 몰랐고, 다른 가전(건조기·제습기·스타일러) 요청도 있었다(`docs/설문-결과.md`).
3. 확장 방향은 1차 뒤에 정했다 (사용자 결정, 11/3): 제조사 협력이나 설명서 자동 수집은 하지 않고, 사용자에게 모델명을 받아 설명서 PDF를 직접 넣는다. 모델 요청이 오면 알림을 받고 싶다고 했다.
4. 캠프 2차 가이드는 "1차를 이어 키우면 1차 대비 무엇이 나아졌는지 보여 달라"고 한다. 2차의 답: **"모델 3개로 고정된 서비스 → 요청하면 늘어나는 서비스"**.
5. 1차 강사 피드백의 "실제 사용자 테스트"는 3~4일차 상호 테스트에서 동기들의 **실제 모델 요청**을 받아 처리하는 것으로 일부 답한다. ("표현이 다른 질문의 검색 실패"는 2차에서 다루지 않는다 → 3.4)

## 3. 범위

### 3.1 최소 기준 — 이 고리 하나를 배포 주소에서 끝까지 돌린다

1. 모델 선택 화면에 "내 모델이 없어요"가 있다. 카테고리는 **세탁기·건조기·에어컨** (사용자 결정). 건조기는 새 카테고리라, 모델이 하나도 없을 때는 빈 목록 안내와 "내 모델이 없어요"만 보인다.
2. 로그인: **이메일 인증 코드(주 방식)**, 같은 이메일이면 **구글 로그인**으로도 같은 계정 (사용자 결정). 질문하기(RAG)는 지금처럼 로그인 없이 된다.
3. 요청 입력: 카테고리·브랜드·모델명. 입력 검사, 이미 있는 모델 안내, 같은 사람 중복 요청 안내.
4. 요청은 Supabase 요청 표에 저장되고, RLS로 **본인 요청만** 보인다 (사용자 결정: 처리는 Supabase 표 화면에서).
5. 새 요청이 오면 **운영자(나)에게 메일**.
6. 운영자가 **모델 추가 도구**로 설명서를 넣고 배포한다.
7. 운영자가 상태를 "추가됨"(또는 "추가 어려움"+사유)으로 바꾸면 **요청자에게 메일**.
8. 요청자가 추가된 모델로 질문한다.

### 3.2 목표 (최소 기준 뒤)

1. 첫 화면 "내 요청" 카드 (대기 / 확인 중 / 추가됨 / 추가 어려움).

### 3.3 여유 시 (순서대로, 사용자 결정 포함)

1. 대화 서버 저장 (로그인이 생긴 뒤, 사용자 결정 "시간이 남으면"). 브라우저 저장 버전 1 형식을 옮기는 방법을 그때 정한다 (결정기록 022 다시 볼 조건).
2. 탈퇴 버튼 (최소 기준에서는 안내 문구 + 요청 시 수동 삭제).
3. 보류한 로그인 방식 (네이버·카카오, 사용자 결정 "보류").

### 3.4 하지 않을 것 (비목표)

1. 질문·답변(RAG) 흐름 변경, 검색 품질 개선 ("찾지 못함" 원인 조사는 2차 밖).
2. 웹 푸시, 내 가전 등록, 서비스센터 연결·리뷰.
3. 글자 없는 PDF 처리(OCR, 3차 계획).
4. 관리자 전용 화면 (Supabase 표 화면으로 대신함).
5. 구글 폼·구글 시트로 요청 받기 (검토 뒤 뺌 → 4절).
6. 기타 가전(스타일러·식기세척기·전자레인지·에어프라이어) 요청 받기. 나중 단계에서 한다 (사용자 결정).

### 3.5 실패로 보는 것 (반목표) — 기능이 돌아가도 이러면 실패

1. 지금 운영의 질문·답변 흐름이 바뀜 (v1.7 쪽 표시 지우기 반영, 임베딩 text-embedding-3-small. 질문 API `app/ask/`와 검색·검증 코드는 손대지 않는다).
2. 모델이 운영 화면에 열리기 **전에** 요청자에게 "추가됨" 메일이 감.
3. 요청자 이메일이 요청 표나 저장소, 로그에 복사됨 (이메일은 Supabase 인증 쪽에만).
4. service 키(관리자 키)나 Resend 키가 화면 코드·저장소·영상에 노출됨.
5. 다른 사람의 요청이 보임.

### 3.6 줄이는 순서 — 밀리면 이 순서로 뺀다 (제안)

1. "내 요청" 카드
2. 구글 로그인 (이메일 코드만으로도 고리는 돈다)
3. 모델 추가 도구의 자동화 일부 (글자 없는 PDF·쪽 표시 검사와 확인 질문 실행은 지표와 안전에 필요해 끝까지 남긴다)
4. Playwright 범위 (메뉴라서 핵심 흐름 1개 테스트는 남긴다)

### 3.7 제약

1. 5일, 개인. 수업 없이 멘토링.
2. 무료 요금제 한도: Supabase 무료 프로젝트는 7일 활동이 적으면 멈춤, Resend 무료 하루 100통, Supabase 사용자 지정 SMTP 발송 시간당 30통에서 시작. 도메인은 첫해 US$1.99(갱신 US$32.12).
3. OpenAI 비용은 장부에 먼저, 운영 잔액 1달러 이상 유지. 장부 상한은 계획 때 정한다 (제안: Fable·v1.9처럼 1달러). 상호 테스트·시연 때 들어오는 운영 질문 비용도 같은 잔액에서 나가므로 3일차 전에 잔액을 확인한다 (제안). 확인용 세트는 봉인 그대로.
4. 개인정보: 요청자 이메일·이름은 저장소·노션·개발일지·영상에 적지 않는다. 테스트 참가자는 코드로만 부른다. 상호 테스트 참가자의 계정·요청 데이터는 **데모데이가 끝난 뒤 지운다** (사용자 결정). 로그인 시트의 안내 문구에 보관 기간을 적는다.
5. 질문·답변(RAG) 코드는 바꾸지 않는다 (3.5).
6. 시험 계정: 개인 메일 대신 **Resend 받기 기능의 시험용 주소**(예: `test1@<우리 계정 id>.resend.app`)를 쓴다 (사용자 제안을 채팅 Claude가 구체화). 이 주소로 온 인증 코드는 Resend 대시보드의 받기(Receiving) 탭에서 보고, Playwright는 Resend 받기 API로 코드를 읽는다. 받은 메일도 Resend 무료 한도(하루 100통)에 포함되니 시험 횟수를 아낀다.

## 4. 검토한 방법과 고른 것

1. **2차 핵심 흐름**: ① 모델 요청 → 추가 → 알림 / ② "찾지 못함" 줄이기 / ③ 막혔을 때 서비스센터 연결. → **①** (사용자 결정). ②는 v1.6·v1.7에서 원인을 확인하지 못했고, 그 뒤 v1.8(Fable 분할)·v1.9(임베딩 large)도 미채택이라 5일 뒤 미채택 위험이 크며 새 흐름이 아니다 (2026-11-20 다시 봄: 이 판단은 그대로). ③은 링크 위주라 개발 이야기와 전후 지표가 약하다.
2. **로그인을 2차에 넣을지**: 요청자에게 알리려면 확인된 연락처가 필요하다. 요청 때 이메일만 받으면 남의 주소로 메일이 갈 수 있다. → **넣는다** (사용자 결정).
3. **로그인 방식**: 구글·네이버·카카오·이메일 인증 전부 / 일부. → **이메일 인증 + 같은 이메일이면 구글** (사용자 결정). 네이버는 서비스 적용 전 검수가 필요하다는 정리 글이 있고(기간 확인 못 함), 카카오는 이메일을 받으려면 비즈 앱 전환이 필요해 보류.
4. **로그인을 어디서**: 지금 서버(FastAPI)에 직접 / Supabase Auth. → **Supabase Auth** (사용자 결정). 이유: 코드 만료·시도 제한·토큰 확인 같은 보안 코드를 직접 쓰지 않음, 같은 이메일 자동 합치기 제공(공식 문서), 캠프에서 배운 Supabase·RLS를 그대로 씀, RAG 서버를 거의 안 건드림. 감수: DB가 둘(설명서=Neon, 계정·요청=Supabase)이 됨. 결정기록 005는 Neon을 고른 이유 중 하나로 "2차 로그인·기록도 같은 DB"를 들었으므로, 이 판단을 바꾼다는 것을 새 결정기록에 005를 밝혀 남김, 무료 프로젝트는 7일 활동이 적으면 멈춤(공식 문서) → 깨우기 예약 호출.
5. **요청 받기·처리**: 구글 폼+시트 / Supabase 표 화면. → **Supabase 표 화면** (사용자 결정). 폼의 "확인된 이메일"은 구글 로그인이 필요해 이메일 코드 로그인과 안 맞고, 시트는 데이터가 두 곳이 되어 상태를 맞춰야 하며 이메일이 드라이브에 복사된다.
6. **메일 보내기**: Apps Script / Gmail SMTP / Resend(도메인 필요). → **Resend + 도메인 pyeobom.help** (사용자 결정: 도메인 구매, 사이트 주소로 씀). Resend는 내 도메인을 인증해야 남에게 보낼 수 있고(공식 문서), vercel.app 주소는 인증할 수 없다(Vercel 커뮤니티 답변).
7. **알림을 보내는 곳**: Supabase Edge Function(TypeScript) / Vercel 파이썬 서버의 알림 주소. → **파이썬** (제안). 새 언어를 늘리지 않고 내가 설명할 수 있는 코드로 둔다. RAG 코드와는 따로인 새 주소만 더한다.

## 5. 화면 흐름 (스케치)

```
[모델 선택 화면]
  ...모델 카드들...
  [ 내 모델이 없어요 ]
        │ 로그인 안 했으면
        ▼
[로그인 시트]  이메일 입력 → [코드 보내기] → 6자리 코드 입력 → 완료
               또는 [Google로 계속하기]
        ▼
[요청 화면]  카테고리(미리 선택) · 브랜드 · 모델명(라벨 위치 안내 링크)
             [요청하기]
        ▼
 ├ 이미 있는 모델 → "이미 있어요" + [바로 질문하기]
 ├ 같은 요청이 있음 → "이미 요청하셨어요"
 └ 접수 → "요청을 받았어요. 추가되면 메일로 알려 드릴게요."
          (목표) 첫 화면 "내 요청" 카드에 상태 표시
```

- 모델명 찾는 법 안내는 1.5차의 "모델명 찾는 법"을 재사용한다.
- 개인정보 안내 문구(로그인 시트): 무엇을 저장하는지(이메일·요청 내용), 왜(추가 알림), 지우는 방법.

## 6. 구조

```
브라우저 (정적 HTML/JS)
  ├─ 질문 API(app/ask) 등 기존 RAG ─► Vercel 파이썬(FastAPI) ─► Neon (설명서)   ← 변경 없음
  └─ supabase-js (공개 키) ─────────► Supabase
                                       ├ Auth: 이메일 코드 · 구글 · 같은 이메일 합치기
                                       │   └ 인증 메일 ─► Resend SMTP (noreply@pyeobom.help)
                                       ├ 요청 표 + RLS (본인만)
                                       └ 데이터베이스 웹훅 ─► Vercel 파이썬 "알림 주소" (새로)
                                                                └ Resend API ─► 운영자 / 요청자
운영자 PC
  └ 모델 추가 도구 (로컬) ─► 검사 · json 항목 · ingest(Neon) · 확인 질문 ─► 보고
```

- 공개(anon) 키만 화면에, service 키는 Vercel 환경 변수에만 둔다.
- Supabase 지역은 결정기록 018의 함수 지역과 사용자 위치를 보고 고른다 (제안, 계획 때 확인).
- 사이트 주소: pyeobom.help (사용자 결정). 옛 주소 pyeobom.vercel.app은 새 주소로 넘겨준다(가능 여부는 연결 때 확인). v1.7~v1.9가 끝나(2026-11-20) 이제 연결해도 된다.

## 7. 데이터 (db.md 초안 수준, 이름은 계획 때 확정)

**요청 표**

1. `id`
2. `user_id` — Supabase 인증 사용자. **이메일은 복사하지 않는다.**
3. `category` — 세탁기 / 건조기 / 에어컨
4. `brand` — 입력값
5. `model_text` — 사용자가 친 모델명 원문
6. `model_key` — 비교용 정규화 값(예: 대문자, 공백·하이픈 제거). 규칙은 계획 때.
7. `status` — 대기 / 확인 중 / 추가됨 / 추가 어려움 (정해진 값만 받게 제약)
8. `reason` — "추가 어려움"일 때 사유 (예: 글자 없는 PDF, 설명서를 찾지 못함)
9. `model_id` — 추가된 경우 `data/models.json`의 id
10. `created_at`, `updated_at`

**규칙**

1. RLS: 본인 행만 넣기·보기. 사용자는 고치기·지우기 불가. 상태는 운영자가 Supabase 표 화면에서 바꾼다.
2. 같은 `user_id` + 같은 `model_key` 중복 금지.
3. 1인 하루 요청 수 제한 (숫자는 계획 때, 제안: 5).
4. 같은 모델을 여러 명이 요청했으면 각자의 행 상태를 바꾸고, 각자에게 메일이 간다.

## 8. 메일

**8.1 인증 코드 메일 (Supabase Auth가 보냄)**

1. Supabase 사용자 지정 SMTP에 Resend를 연결한다: 호스트 `smtp.resend.com`, 포트 465, 사용자명 `resend`, 비밀번호 = Resend API 키 (Resend 공식 문서). Resend 연동 화면에서 자동으로 채우는 방법도 있다.
2. "Magic Link" 템플릿에 `{{ .Token }}`을 넣어 6자리 코드로 보낸다 (Supabase 공식 문서).
3. 기본값: 같은 사람 60초에 1번 요청, 코드 1시간 유효, 사용자 지정 SMTP의 프로젝트 전체 발송은 시간당 30통에서 시작(조정 가능). Resend 무료는 하루 100통. 값을 바꿀지는 계획 때.

**8.2 알림 메일 (우리 서버가 보냄)**

1. 웹훅: 요청 표에 새 행 → 운영자에게 / `status`가 추가됨·추가 어려움으로 바뀜 → 요청자에게.
2. 파이썬 알림 주소는 웹훅에 넣은 **비밀 값 헤더**를 확인하고, 아니면 거절한다.
3. 요청자 이메일은 service 키로 Supabase에서 그때 조회해 보내고 저장·로그에 남기지 않는다.
4. 메일 실패는 서버 로그에만 남기고(주소는 가림), 운영자가 다시 보낼 수 있게 한다 (방법은 계획 때).

**8.3 순서 규칙**

순서 (제안): ① 설명서 조각을 DB에 넣는다 → ② 배포 전에 로컬에서 운영과 같은 답변 경로로 확인 질문을 돌려 합격선(9.3)을 판정한다 → ③ 합격이면 배포하고 운영 화면에서 그 모델이 보이는지 확인한다 → ④ 그 **뒤에만** "추가됨"으로 바꾼다.

- 미달이면 운영에 열지 않는다 (모델 목록 `data/models.json`을 배포하지 않음).
- 모델 목록이 배포되기 전에는 DB에 조각이 있어도 화면·질문 API에서 새 모델이 열리지 않는다고 보고 있다. 계획 때 확인한다 (14절).
- 이 순서를 모델 추가 도구의 마지막 체크리스트에 넣는다.

## 9. 모델 추가 도구와 측정

**9.1 지금 방식 (1일차에 실제로 하며 단계·시간 기록)**

알려진 단계: 설명서 PDF 확보·이용 조건 확인 → `data/documents.json` 항목 → `data/models.json` 항목(화면용 이름·모델 코드·진단 안내 등) → 해결 가이드 연결(모델 단위로 판단, 기능에 묶인 가이드는 그 기능이 있는 모델에만, 결정기록 014) → `python -m ingest --doc-id` (v1.7 뒤로 설명서 경로에서 쪽 표시를 자동으로 지움) → `data/error_codes.json`·브랜드 별칭(새 브랜드일 때) → 제품 일러스트(결정기록 025) → 확인 질문 쓰기·실행·판정 → 배포. 빠진 단계는 1일차 기록으로 채운다.

**9.2 도구가 맡을 것 / 사람이 할 것 (제안)**

- 도구: 글자 없는 PDF(결정기록 014) 자동 검사, **쪽 표시가 지워졌는지 검사**, 두 json 항목 초안 만들기, ingest 실행, 에러 코드 후보 뽑기, 확인 질문 실행(배포 전 로컬, 운영과 같은 답변 경로)과 결과 표, 마지막 체크리스트 출력.
  - 쪽 표시 검사가 필요한 이유: 지금 지우는 규칙은 쪽 글의 앞 20자만 보고, 기존 설명서 3개로만 시험했다(`docs/평가/v17-extraction.md`). 새 설명서에서 쪽 표시가 남아 보이면 멈추고 보고한다 (제안).
- 사람: PDF 고르기와 이용 조건 확인, json 항목 확인, 해결 가이드 연결 판단, 확인 질문 쓰기(9.3-7의 구성, 설명서 원문 대조, 답이 있는 쪽 모두 적기), 판정, 일러스트, 배포, 상태 바꾸기.
- 적재는 지금 운영 설정 그대로 한다: 임베딩 text-embedding-3-small, `OPENAI_EMBED_DIMENSIONS`는 비워 둠(`EMBED_DIM`과 헷갈리지 않게). v1.9 임베딩 large는 미채택이다(결정기록 036).
- DB 데이터를 지우는 단계는 사람 확인 뒤에만 (CLAUDE.md 규칙).
- AI 비용(임베딩·확인 질문 답변)은 장부에 먼저 적고 실행.

**9.3 측정 (판단 기준 — 측정 전에 확정, 결과를 본 뒤 바꾸지 않음)**

1. 지표: **모델 1개를 추가하는 추가 작업 시간(분)**과 **사람이 직접 한 단계 수**.
2. 재는 범위 (사용자 결정 2026-11-20): PDF 파일을 손에 넣은 시점 → 운영 화면에서 그 모델이 보일 때까지에서 **확인 질문 쓰기·판정·배포 대기를 뺀 시간**("추가 작업 시간")으로 비교한다. 전체 시간도 함께 적는다. 사람 단계 수도 같은 범위에서 센다.
   - 이유: 비교용 모델을 다시 넣을 때는 1일차에 쓴 확인 질문을 그대로 써서 질문 쓰기가 0분이 된다. 전체 시간으로 비교하면 도구와 상관없이 빨라 보인다.
3. 기록 방법 (제안): 시간 기록지에 단계마다 시작·끝 시각을 적는다. 쉬는 시간은 "멈춤" 줄로 적고 뺀다. 사람 단계 = 기록지에서 사람이 손이나 판단을 쓴 줄(입력, 고르기, 결과를 읽고 진행을 정함, 명령 실행). 도구나 배포를 기다리기만 한 줄은 세지 않는다. 기록지 양식은 계획 때.
4. 전: 1일차, 비교용 모델을 지금 방식으로.
5. 후: 도구로 ① 비교용 모델을 같은 조건으로 다시, ② 상호 테스트에서 실제로 요청된 모델 최대 2개. ②는 개선 판정에 쓰지 않고 기록만 한다 (판정은 ① 하나의 숫자로).
6. 개선 판정 기준 (사용자 결정 2026-11-17, 재는 범위는 2026-11-20): 비교용 모델 재추가의 **추가 작업 시간이 전의 절반 이하**이고 **사람이 직접 한 단계 수가 줄면** 개선. 둘 중 하나라도 못 맞추면 "개선 확인 못 함"으로 기록한다.
7. 확인 질문 구성 (사용자 결정 2026-11-20): 10개 = 설명서 앞·중간·뒤에서 고르게 고른 사용법·기능·관리 질문 8개 + 설명서나 연결한 해결 가이드에 실제로 있는 에러 코드 질문 2개.
   - 원문에 에러 코드가 없으면 10개를 고르게 뽑는다.
   - 함정 질문(설명서에 없는 내용)은 넣지 않는다.
   - 질문과 정답 쪽(답이 있는 쪽 모두)은 **적재 전에** 쓰고 파일 해시를 커밋한다.
   - 비교용 모델은 전·후에 같은 질문을 쓴다.
8. 합격선 (모델마다, 사용자 결정 2026-11-17): 사람 판정으로 **정답 8개 이상 · 환각 0**.
   - 판정 규칙: `docs/평가/평가-규칙.md` "사람 판정"(결정기록 033 덧붙임 규칙 포함). 비교할 상대 방법이 없어 가린 판정은 하지 않고, v1.9 판정 화면의 원문 보기·검색 기능은 다시 쓴다 (제안).
   - 경계 판정 (사용자 결정 2026-11-20): 경계 판정을 오답·환각 쪽으로 뒤집어도 합격선을 넘을 때만 합격이다. 합격하면 실제 요청자에게 "추가됨" 메일이 가기 때문이다.
   - 미달이면 운영에 열지 않고(8.3) "추가됨"으로 바꾸지 않으며 원인을 기록한다. 질문 세트를 결과에 맞춰 고치지 않는다.
   - 적재 문제(추출·쪽 표시·json·가이드 연결)를 고친 경우에만 같은 질문으로 다시 돌린다 (제안: 1번까지, 계획 때 측정 전에 확정). 실제 요청 모델이 끝내 미달이면 "추가 어려움"(사유 적음)으로 바꾼다 (제안).
9. 결정기록 032 "다시 볼 조건"과의 관계 (제안): 확인 질문에서 "설명서에 없는 코드에 다른 코드의 해결 절차를 붙이는" 환각(032의 267 사례)이 나오면 그 모델은 환각 0을 못 맞춰 불합격이다. 이 답은 032의 근거로 기록만 하고, 쪽 표시 지우기를 다시 정하는 일은 2차 뒤에 한다 (2차는 질문·답변 코드를 바꾸지 않음, 3.4·3.5).
10. 한계로 적을 것: 같은 모델을 두 번째 넣을 때는 손에 익어 빨라지는 효과가 섞인다. 그래서 처음 보는 모델(5의 ②)도 함께 잰다. 표본이 작다.
11. 비교용 모델 후보 (제안): 글자가 있는 PDF + 지금 있는 브랜드(삼성·LG) + **지금 있는 카테고리(세탁기·에어컨)** 제품. 건조기 카테고리를 만드는 시간이 전후 비교에 섞이지 않게 하려는 것이다. 1일차에 정한다.
12. 비교용 모델 재추가 절차: 비교용 모델의 json 항목과 운영 조각 중 그 문서의 행만 되돌린 상태에서 도구로 다시 넣는다. 기존 3개 모델의 조각과 실험 조각(`bundle_chunks`)은 건드리지 않는다. DB 조각 삭제는 사용자 확인 뒤.

## 10. 안정성 — 시연할 것 (가이드: 2가지 이상)

1. 빈 입력·이상한 모델명 거절, 이미 있는 모델 안내, 중복 요청 안내.
2. 다른 계정으로 로그인하면 내 요청이 안 보임 (RLS 시연).
3. 인증 코드 반복 요청 제한 (60초), 틀린 코드.
4. 로그인 없이 요청 시도 → 로그인으로 안내.
5. 글자 없는 PDF를 도구가 자동으로 거절.
6. 메일 실패 시 화면 안내.
7. Supabase가 멈추거나 응답이 없을 때: 질문하기는 그대로 되고, 로그인·요청만 "잠시 쓸 수 없어요" 안내.
