## 1. 왜 하나

- 펴봄이 "찾지 못함"으로 답하는 가장 큰 원인은 검색이다. v1.7 3단계(개발용 21문장, 운영)에서 찾지 못함 12개 중 9개, 2회차 8개 중 7개는 기대 근거 쪽이 검색 5개 안에 없었다(2026-11-20 사전 확인).
- 지금까지 조각 쪽을 바꾼 방법(추출 도구, 소제목 자르기, Fable 자르기)은 개발용 검색을 7~8에서 올리지 못했다. 질문 쪽을 바꾼 방법 중 "질문 미리 만들기"만 검색 8→11을 냈지만 답변 정답은 +1이었다(029).
- 운영에서 놓친 정답의 대부분은 20위 밖이다(개발용 20문장 중 21~100위 8개). 질문과 설명서의 말이 많이 다를 때 지금 임베딩 모델이 둘을 가깝게 보지 못한다는 뜻일 수 있다(확인하지 못함). 그래서 질문과 조각을 숫자로 바꾸는 모델 자체를 더 큰 모델로 바꿔 본다.
- 사용자 결정(2026-11-20): 캠프 2차(11/25) 전에, 운영 반영까지 한다. 일정이 밀리면 운영 반영만 2차 뒤로 미룬다(결론까지는 2차 전에).

## 4. 방법 고르기 (Approaches)

사용자가 고른 것(2026-11-20): **A. 임베딩 모델 바꾸기.**

1. **A. 임베딩 모델 바꾸기 (채택)** — `text-embedding-3-large`, 결과 길이 1536(`dimensions` 매개변수)
   - 공식 자료: OpenAI가 3-large를 발표하며 결과 길이를 `dimensions`로 줄일 수 있다고 밝혔다. 발표된 다국어 검색 시험(MIRACL) 평균은 small 44.0, large 54.9다(3072차원 기준). 1536으로 줄였을 때 얼마나 내려가는지, 우리 한국어 문장에서 오를지는 확인하지 못했다. 가격은 100만 토큰당 0.13달러(small 0.02달러).
   - 장점: 질문마다 추가 호출이 없어 기존 비용·시간 기준을 그대로 쓸 수 있다. 1536이라 DB 열을 바꾸지 않는다. 같은 OpenAI 키를 쓴다. 놓친 정답 전체(20위 밖 포함)를 겨냥한다.
   - 대가: 운영 반영 때 조각 전체(설명서 297 + 가이드 35)를 다시 임베딩하고 질문 쪽 모델도 함께 바꿔야 한다(8절).
2. **B. 넉넉히 찾고 재정렬 서비스로 다시 줄 세우기 (이번에 안 함)**
   - 6~50위 정답을 겨냥한다(검색 때문에 못 찾은 9문장 중 5개).
   - Voyage 재정렬 공식 가격 100만 토큰당 0.05달러(세는 법: 질문 토큰 × 문서 수 + 문서 토큰). 조각 50개 기준 질문당 약 0.0016달러로 추정 → 지금 질문당 비용의 약 5배. Cohere는 공식 가격 페이지에 재정렬 숫자가 없다(제3자 자료 검색 1회 0.001~0.0025달러). 응답 시간은 제3자 자료로 0.3~0.6초(우리 환경에서 재지 않음).
   - 기존 B-2(비용 1.5배 이하)로는 통과하기 어렵다. 하려면 측정 전에 비용 기준을 다시 정해야 하고, 새 업체 계정·키가 필요하다. 다음 후보로 남긴다.
3. **C. 넘기는 조각 수 늘리기(5→10) (뺌)**: 6~10위가 개발용 2문장뿐이라 +3에 닿을 수 없다.

## 5. 후보 정의

1. 이름(사용자 결정 2026-11-20): 실험 이름 **임베딩 모델 바꾸기**, 노션 개발 타임라인 단계 **v1.9**. 후보 코드 이름은 `emb_large`(채팅 Claude 기본값, 코드 이름이라 보고에만 적음). 기록에는 "임베딩 large"처럼 풀어 쓴다.
2. 글·조각: 운영 `chunks`와 **글·쪽·문서·순서가 같다**. 설명서 297개와 가이드 35개 모두. 바뀌는 것은 임베딩뿐이다.
3. 임베딩: `text-embedding-3-large`, `dimensions=1536`. 조각과 질문 모두 같은 설정. 정규화·거리 계산은 운영과 같게 한다(pgvector 코사인 거리, 지금과 같은 연산자).
4. 측정 방식: 실험 조각 표(`bundle_chunks`)에 후보를 넣고, 한 실행 안에서 운영과 후보를 함께 잰다. 지금 측정 코드(`measure/v17_stage1.py`의 `measure_sets`)는 모든 벌에 질문 임베딩 함수 하나를 쓰므로, **벌마다 질문 임베딩 모델을 따로 쓰도록** 바꿔야 한다. 운영 벌은 지금과 똑같이(small, `dimensions` 없음) 재야 한다.
5. 가이드 조각: Fable 때는 운영에서 임베딩까지 그대로 복사했다. 이번에는 가이드 조각도 후보 모델로 다시 임베딩한다. 기대 근거 `chunk:300`·`chunk:312`(가이드 조각 번호)가 그대로 세어지도록 번호를 지킨다.
6. 운영 코드 변경(채택 전에도 넣는 부분): 임베딩 요청에 차원을 넘길 수 있게 한다. **운영 동작은 반영 전까지 바뀌지 않아야 한다**(지금 설정에서는 요청 인자가 지금과 같음을 테스트로 확인).

## 8. 운영 반영 (채택됐을 때만)

1. 백업(git 밖): 운영 `chunks`의 id·임베딩 전부. 되돌리기 시험(백업에서 한 행을 읽어 대조) 뒤 진행.
2. 새 임베딩 만들기: 4단계 후보와 같은 설정으로 운영 조각 전부(장부 행 먼저). 0단계 후보 조각 임베딩을 다시 써도 되는지는 계획에서 정한다(글이 같음을 확인했을 때만).
3. 바꾸기: 운영 환경 변수(`OPENAI_EMBED_MODEL`, 차원 설정)와 `chunks` 임베딩을 함께 바꾼다. Vercel 환경 변수는 다시 배포해야 반영되므로, DB 구조를 바꾸지 않으면 최소한 다시 배포하는 시간만큼은 질문 모델과 조각 모델이 섞인다. 허용 시간과 방법(사용자 결정 2026-11-20): **DB 구조는 바꾸지 않고 짧게 허용한다.** 사용자가 적은 시간에, 새 환경 변수로 다시 배포해 그 배포가 운영에 올라가는 순간 `chunks` 임베딩을 한 트랜잭션으로 바꾼다(보통 1분 안팎 예상, 재지 않음). 섞인 시간의 상한은 **15분**이고, 넘으면 되돌린다. 실제 섞인 시간(배포 운영 반영 시각 ~ 트랜잭션 끝 시각)을 기록한다. Vercel 환경 변수는 사용자가 대시보드에서 바꾼다(값은 Claude Code가 보지 않음).
   - 반영 전 확인: 미리보기(Preview) 배포가 운영 DB를 같이 쓰는지(Claude Code가 `vercel env ls`로 이름과 적용 환경만 확인, 값은 보지 않음). 같이 쓰면 반영하는 동안 미리보기도 섞이고, 미리보기에서 미리 시험할 수 없다.
4. 확인: `/api/health`, 5C 질문 1회, 운영 30문항 2회 사용자 판정(합격선 24/30 이상·환각 0, v1.7 9단계와 같음).
5. 되돌리기 조건: 4의 합격선 미달이나 오류. 백업과 환경 변수로 되돌린다(DB 작업은 사용자 확인 뒤).
6. 적재 코드는 같은 함수를 쓰므로, 반영 뒤 새 모델을 넣을 때도 새 설정을 쓴다(2차 모델 추가 도구와 맞음).
