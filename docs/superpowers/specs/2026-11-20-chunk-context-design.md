## 1. 왜 하나

- 지금 운영(small)이 틀리는 이유는 대부분 검색이다. v1.9 3단계 결과 CSV(`evaluation/results/emb-s3-r1·r2`)의 운영 벌을 나눠 보면(비용 0, 2026-11-20, 채팅 Claude) 틀린 답 19개 중 17개는 정답 근거가 검색 5개(+진단 덧붙임) 안에 없었고, 2개만 근거를 받고도 "찾지 못함"이었다(p16-1·p22-2 각 2회차). 답변 쪽을 고쳐서는 많아야 2개라 합격선 +3에 닿을 수 없다.
- v1.9 임베딩 large는 검색 8 → 14, 정답 10 → 16(기록용)이었지만 응답 시간 조건으로 미채택이다(036). 같은 실험의 기준은 바꾸지 않는다.
- 029의 M1(조각 앞에 "모델 · 문서 제목 · 장 이름 · 소제목" 한 줄을 붙여 다시 임베딩)은 개발용 8 → 10(+2)으로 +3에 못 미쳤다. 형식이 정해진 제목 대신, 그 조각이 무엇을 다루는지 AI가 문장으로 설명하면 더 오를 수 있다(확인하지 못함).
- 외부 근거: Anthropic은 조각마다 짧은 문맥을 AI로 써서 붙인 뒤 임베딩하면 상위 20개 검색 실패가 평균 35% 줄었다고 발표했다(코드·소설·논문 등 영어 자료, 우리 한국어 설명서에서는 확인하지 못함).
- 이 방법은 설명을 적재할 때 한 번만 쓰므로 질문마다 하는 일(호출 수)이 늘지 않는다.
- 사용자 결정(2026-11-20): 2차(11/25) 전에, 운영 반영까지 한다. 일정이 밀리면 운영 반영만 2차 뒤로 미룬다. 방법은 "조각 설명 붙이기"(추천대로).

## 2. 목표 · 비목표 · 반목표

- 목표: 측정 전에 정한 기준(6절)으로 "조각 설명 붙이기"의 채택 여부를 정하고, 채택되면 2차 전에 운영에 반영한다.
- 비목표: 임베딩 모델 바꾸기(small 그대로), 키워드 검색(BM25) 더하기, 재정렬, 넘기는 조각 수, 조각 자르기·추출, 답변 프롬프트·답변 모델, 화면, 설명 쓰는 모델끼리 비교. 한 번에 하나만 바꾼다.
- 반목표(기술적으로 돌아가도 실패로 보는 것):
  - 결과를 본 뒤 기준·설명 요청문·설명 모델·평가 세트를 고치는 것
  - 설명을 쓰는 AI가 평가 정보(평가 문장, 정답 쪽, v1.7·v1.9에서 못 찾은 쪽, 그 쪽을 예로 든 설명)를 보는 것
  - 같은 요청문을 여러 번 돌리거나 여러 모델로 돌려 좋은 결과를 고르는 것
  - 화면 인용, 답변 AI가 받는 글, 인용 검사에 설명이 들어가는 것(검색에만 쓴다)
  - 측정한 설명과 운영에 반영한 설명이 다른 것(다시 써서 반영하는 것)
  - 확인용 세트를 4단계 전에 여는 것
  - 되돌릴 수 없는 운영 DB 작업(백업 없이 덮어쓰기)

## 3. 지금 상태와 사전 확인

- 기준점은 **지금 운영**이다: `chunks` 332개(설명서 297 + 가이드 35, 쪽 표시 지운 조각), 임베딩 `text-embedding-3-small` 1536차원(`OPENAI_EMBED_DIMENSIONS` 비어 있음), 벡터 검색 상위 5개, 근거에 없는 에러 코드는 진단 안내 쪽 덧붙임, 답변 `gpt-6-luna`(추론 low)(015, 036).
- 지금 임베딩 입력은 조각 본문 그대로다(적재 코드와 실험 조각 저장이 같은 임베딩 함수를 씀). 빌더가 계획 첫 단계에서 코드로 확인한다.
- 측정 도구: v1.9의 `measure_sets`(벌마다 질문 임베딩, 이 실험 벌은 운영과 같은 small 질문 임베딩), `bundle_deps`, `stage2 --blind`, `check_budget`, 결과 CSV의 `found`·`latency_ms`·`llm_ms`.
- 사전 확인(2026-11-20, 비용 0): 운영 벌 틀린 답 19개 = 근거 없음·찾지 못함 15, 근거 없음·답함 2(p19-1), 근거 받음·찾지 못함 2(p16-1·p22-2 2회차). 임베딩 large 벌은 틀린 답 9개 = 검색 6, 답변 3.
- v1.9 응답 시간 관찰(원인 확인 아님): 찾은 답(답변 AI 약 3.8초)이 찾지 못한 답(운영 약 2.3초)보다 길고, 두 벌 모두 찾은 답끼리는 +81ms였다. 029의 질문 미리 만들기(질문당 호출 0)도 같은 실행 안 +400ms였다.

## 4. 방법 고르기 (Approaches)

사용자가 고른 것(2026-11-20, "추천대로"): **A. 조각 설명 붙이기.**

1. **A. 조각 설명 붙이기 (채택)** — AI가 조각마다 "어느 설명서의 어느 부분에서 무슨 기능·문제·상황을 다루는지" 1~2문장을 쓰고, 그 문장을 조각 본문 앞에 붙여 임베딩한다. 저장되는 본문·화면·답변 AI는 원문 그대로다.
   - 장점: 질문마다 호출이 늘지 않는다. 적재할 때 한 번만 비용이 든다(약 0.1~0.2달러 어림). 검색 실패(오답의 대부분)를 겨냥한다.
   - 대가: "조각에 글을 덧붙이지 않는다"(v1.7·Fable 설계) 원칙을 "검색용으로만은 붙여도 된다"로 바꾼다(사용자 결정). 029 M1(+2)과 비슷한 효과에 그칠 수 있다. 적재에 AI 단계가 하나 늘어 새 모델을 넣을 때 시간·비용이 조금 늘어난다.
2. **B. 재정렬(리랭커) (이번에 안 함)** — 외부 근거는 가장 탄탄하지만 질문당 비용이 약 5배(임베딩 설계 4절 추정)이고 시간도 늘어, 측정 전에 비용·시간 기준을 새로 정해야 하고 새 업체 키가 필요하다. 다음 후보로 남긴다.
3. **뺀 것**
   - 임베딩 large를 시간 기준만 바꿔 다시 재기: 결과(찾은 답끼리 +81ms)를 알고 정하는 기준이라 결과에 맞춘 조정이 된다.
   - 한국어 전용 임베딩 모델(KURE 등): 질문 임베딩 서버를 따로 띄워야 해 4일 안에는 무리.
   - 답변 쪽(찾지 못함 과잉 거절 줄이기): 운영 기준 많아야 2개라 +3에 닿지 않는다.

## 5. 후보 정의

1. 이름: 노션 개발 타임라인 단계 **v1.95**(사용자 결정 2026-11-20). 실험 이름 **조각 설명 붙이기**(채팅 Claude 기본값). 후보 코드 이름은 빌더가 정해 보고에만 적는다. 기록에는 "조각 설명"처럼 풀어 쓴다.
2. 글·조각: 운영 `chunks`와 글·쪽·문서·순서·번호가 같다(설명서 297 + 가이드 35). 저장하는 본문(`content`)은 원문 그대로다.
3. 임베딩: 입력 = 설명 + 줄바꿈 + 원문 본문. 모델은 `text-embedding-3-small`, 차원 설정 없음(운영과 같음). 질문 임베딩은 운영과 같다(바뀌지 않음).
4. 설명 쓰기 (사용자 결정: OpenAI 모델로, 적재 코드에 넣는다)
   - 모델: `gpt-6-luna`, 추론 low(채팅 Claude 기본값).
   - **설명 모델은 답변 모델과 따로 고정한다**(채팅 Claude 기본값, 승인 때 사용자 질문으로 덧붙임 2026-11-20). 설정을 따로 두고 운영 설정 기록(`run_config.PRODUCTION`)에 남기며, 실행 설정이 다르면 경고한다. 답변 모델을 나중에 바꿔도 설명 모델이 몰래 바뀌지 않게 하기 위해서다. 이 실험 결과는 이 모델·이 설정으로 쓴 설명에 대한 것이고, 다른 모델로 쓴 설명도 같은 효과라는 근거는 없다.
   - 입력: 설명서 이름(모델명), 그 조각이 있는 쪽의 글 전체(운영 적재와 같은 쪽 글), 그 조각 본문. 가이드 조각은 가이드 제목과 같은 가이드의 글 전체(채팅 Claude 기본값). 설명서 전체는 넣지 않는다(비용).
   - 출력: 한국어 1~2문장, 150자 이하. "이 조각이 어느 설명서의 어떤 기능·문제·상황·절차를 다루는지". 원문에 없는 숫자·절차·이름을 만들지 않는다.
   - 요청문 원문은 계획에서 고정하고 사용자가 확인한다. 넣지 않는 것: 평가 문장, 정답 쪽, 못 찾은 쪽, 특정 쪽을 예로 든 설명.
   - **한 번만 돌린다.** 다시 돌리는 것은 API 오류와 형식 오류(빈 설명, 150자 초과)가 난 그 조각만이고, 횟수를 기록한다. 그래도 설명이 없는 조각이 하나라도 있으면 멈추고 보고한다.
   - 설명 원문은 git 밖에 조각 번호·본문 해시·설명 모델과 함께 저장한다. 리포트에는 수·길이·해시만 적는다. 측정과 운영 반영은 이 파일의 설명을 그대로 쓴다(다시 쓰지 않는다).
5. 측정: v1.9와 같은 도구로, 실험 조각 표(`bundle_chunks`)에 새 벌을 넣고 운영과 한 실행 안에서 함께 잰다.
6. 운영 코드: 실험과 반영이 같은 설명을 쓰도록, 설명 쓰기와 "설명 붙여 임베딩"은 적재 코드와 측정 코드가 함께 쓰는 함수로 만든다. **운영 동작은 반영 전까지 바뀌지 않아야 한다**(설정이 없으면 지금과 같은 입력으로 임베딩, 테스트로 확인).

## 6. 단계와 채택 기준 (측정 전 확정, 결과를 본 뒤 바꾸지 않음)

**공통** (채팅 Claude 기본값)
- 숫자는 v1.9(=v1.7·Fable)와 같다. 응답 시간 세는 법만 다르다(아래 B-2, 사용자 결정).
- **여러 회차 숫자는 두 회차를 합쳐 센다**: 사람 판정 정답은 ⑰(두 회차 모두 정답이어야 정답, 한 번이라도 환각이면 환각), 질문당 비용과 응답 시간은 두 회차를 합친 평균. 계획에 그대로 적는다(v1.9 교훈, 036).
- 세는 법·측정 세트·⑰·덧붙임 판정 규칙(033)은 v1.9 설계 6절과 같다. 판정지 머리말에는 033 규칙을 넣는다(v1.9 최종 검토 권고 4).

### 0단계: 준비

1. 장부 행(설명 쓰기 + 임베딩)을 먼저 적고 `check_budget` 통과 뒤 설명 쓰기(332개).
2. 형식 확인: 빈 설명 0, 150자 초과 0, 다시 돌린 수 기록.
3. 표본 대조(채팅 Claude, 사람 판정 아님): 무작위 20개(시드 고정)를 그 쪽 원문과 대조한다. 원문에 없는 숫자·절차·버튼·기능 이름이 하나라도 있으면 멈추고 사용자가 정한다(요청문을 고쳐 한 번 더 돌릴지, 미완료로 둘지). 평가 정보를 보지 않은 상태의 확인이라 측정 결과에 맞춘 조정이 아니다.
4. 임베딩(small) → 새 벌 저장 → 운영과 글·쪽·문서·번호 대조(어긋남 0이 아니면 멈춤) → 운영 벌 1~20위가 v1.9 1단계 결과와 같은지 대조(다르면 멈춤).

### 1단계: 검색만 (한 실행 안에서 운영·후보)

- **B-1**: 개발용 P 5위 안이 운영보다 3문장 이상 많음(20문장 중) **그리고** 30문항 5위 안이 운영보다 1문항 넘게 떨어지지 않음.
- 기록용: 순위 구간(1~5/6~10/11~20/21~30/31~50/51~100/100위 밖)과 문장별 순위 변화, 029 M1·v1.9 large와 나란히 적기.
- 통과하지 못하면 미채택으로 기록하고 끝낸다. 확인용 세트는 봉인을 유지한다.

### 3단계: 답변까지 (개발용 21문장, 운영과 후보 각 2회, 한 실행 안)

- 판정: 사용자가 전부, 방법 이름을 가린 판정지로. 대응표 해시를 판정 전에 커밋. 덧붙임 규칙(033), ⑰.
- **B-2**:
  - 사람 판정 정답이 운영보다 3문장 이상 많음(21문장 중), 환각 0
  - 질문당 비용이 운영의 1.5배 이하(두 회차 합친 평균)
  - **응답 시간(사용자 결정 2026-11-20)**: 같은 실행에서 같은 문장·같은 회차에 **두 벌 모두 `found`가 true인 쌍**만 모아, 응답 시간(`latency_ms`) 차이(후보 − 운영)의 평균이 +500ms 이하. 두 회차의 쌍을 모두 합쳐 평균한다.
    - 쌍이 10개 미만이면 전체 답 평균(두 회차 합친)으로 판정한다(채팅 Claude 기본값).
    - 기록용: 전체 답 평균 차이도 함께 적는다(앞 실험들과 견주기 위해).

  - 5C 확인 3회 모두 찾음(v1.9와 같은 정의).

## 8. 운영 반영 (채택됐을 때만)

1. 질문 임베딩 모델이 그대로라 환경 변수·다시 배포가 필요 없다. 조각 임베딩만 한 트랜잭션으로 바꾸므로 질문과 조각의 모델이 섞이는 시간이 없다(v1.9와 다름).
2. 백업(git 밖): 운영 `chunks`의 id·임베딩 전부. 되돌리기 시험(백업 한 행을 읽어 대조) 뒤 진행.
3. 새 임베딩: 4단계 후보와 같은 설명·같은 입력. 실험 벌의 임베딩을 그대로 쓴다(글이 같음을 확인했을 때만, v1.9 계획 Task 6과 같은 방식).
4. 바꾸기: 332행, 바뀐 행 수가 다르면 전체 되돌림(v1.9 `swap_embeddings`와 같은 동작).
5. 확인: `/api/health`, 5C 질문 1회, 운영 30문항 2회 사용자 판정(합격선 24/30 이상·환각 0, v1.9 설계 8절과 같음). 미달·오류면 백업으로 되돌린다(DB 작업은 사용자 확인 뒤).
6. 적재 코드: 반영 뒤 새 조각을 넣을 때도 같은 함수와 같은 고정 설명 모델로 설명을 쓰고 붙여 임베딩한다(2차 모델 추가 도구와 맞음). 설명은 DB에 넣지 않고(구조 변경 없음) 조각 번호·본문 해시·설명 모델과 함께 git 밖 파일로 남긴다(채팅 Claude 기본값).
7. **2차 설계와의 관계 (사용자 결정 2026-11-20: 채택되면 원래대로 11/24에 반영)**: 승인된 2차 설계(3판)는 "운영 그대로(v1.8·v1.9 미채택)"를 출발점으로 하고 "적재는 지금 운영 설정 그대로"(9.2), 1일차에 비교용 모델을 "지금 방식"으로 넣어 추가 작업 시간을 잰다(9.3). 이 실험을 반영하면 그 "지금 방식"에 조각 설명 단계가 들어간다. 그래서 반영을 마치면 2차 설계에 덧붙임을 넣는다(문구는 채팅 Claude 초안, 사용자 확인): 출발점에 v1.95 반영, 적재 설정에 설명 모델, 1일차 "전" 측정과 모델 추가 도구 모두 설명 단계를 포함. 반영하지 않으면(미채택·채택 후보·미완료) 2차 설계는 그대로다.

## 12. 한계와 위험

- 개발용 20·21문장이라 1~2문장 차이는 우연과 구분하기 어렵다(그래서 +3).
- Anthropic 수치는 영어·다른 분야 자료다. 029 M1이 +2였던 것처럼 비슷한 효과에 그칠 수 있다.
- 설명은 모델마다, 같은 모델도 돌릴 때마다 달라질 수 있다. 한 번 쓴 설명을 파일로 남겨 측정과 반영에 같이 쓰므로 운영은 측정한 상태와 같다. 다른 모델의 설명이 더 나은지는 재지 않는다(다음 후보).
- 설명 요청문을 쓰는 채팅 Claude는 개발용 문장과 못 찾은 쪽을 알고 있다. 요청문에 넣지 않는 것으로 막지만, 쓰는 사람이 안다는 사실은 남는다(Fable 설계 11절과 같은 한계).
- 설명 AI가 원문과 다른 내용을 쓰면 검색을 엉뚱하게 이끌 수 있다(표본 20개 대조로 일부만 막음).
- 응답 시간 세는 법이 앞 실험들과 달라 숫자를 그대로 견줄 수 없다(전체 평균도 기록용으로 함께 적음).
- 적재에 AI 단계가 늘어 2차 모델 추가 시간·비용이 조금 는다(2차 개선 기준 "재추가 총 시간"과 함께 본다).
- 2차 준비(도메인·계정·2차 세부 계획)와 시간이 겹친다. 반영하면 2차 출발점과 적재 방식이 2차 하루 전에 바뀐다(8절 7).
