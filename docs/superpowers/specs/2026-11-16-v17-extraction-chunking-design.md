## 2. 목표 · 하지 않는 것 · 실패로 볼 것

**목표**
1. 설명서 PDF에서 글을 뽑는 도구를 넓게 비교하고, 검색 결과로 고른다.
2. 고른 도구의 제목 정보로 조각을 소제목 단위로 잘라 본다.
3. 쪽 표시를 지운다.
4. 측정 전에 정한 기준을 통과한 변경만 운영과 적재 코드(`python -m ingest`)에 반영한다. 앞으로 넣을 모델도 같은 방식으로 들어가게 하기 위해서다(계획 1-5).

**하지 않는 것**
- 해결 가이드(HTML)의 추출과 조각은 바꾸지 않는다.
- 검색 방식(벡터, `TOP_K=5`), 답변 프롬프트(v1), 답변 모델, 인용 검사는 바꾸지 않는다.
- Fable 분할(AI가 설명서를 나누기)은 다음 대화에서 따로 한다. 이번 결과는 그때 "규칙으로 자른 것"의 비교 대상이 된다.
- 조각 앞에 제목 붙이기(M1), 질문 만들기(M2), 용어 사전(M3)은 다시 시험하지 않는다.
- DeepEval은 쓰지 않는다. 사람 판정이 최종 기준이고, 비용을 줄이기 위해서다.
- 인용 규칙과 운영 이유 코드는 다음 후보로 둔다.

**실패로 볼 것** (기술적으로 돌아가도)
- 평가 세트를 보고 방법이나 숫자를 고치는 것
- 확인용 세트를 4단계 전에 검색·채점하는 것
- 결과를 본 뒤 기준을 바꾸는 것
- 숫자가 바뀌는 추출("4.0 kg"이 "4 0 kg"이 되는 것)을 받아들이는 것
- 쪽 번호가 지금과 달라져 근거 표시("사용설명서 N쪽")가 틀리는 것
- 화면에 보이는 인용에 마크다운 기호가 섞이는 것
- 설명서 본문이나 조각 글이 공개 저장소에 들어가는 것(결정기록 009, 기획서)
- 사용자 확인 없이 운영 DB를 바꾸는 것

## 4. 고려한 방법

- **가. 글자 뽑기만 바꾸기**: 도구마다 뽑은 글을 지금처럼 800자로 잘라 검색을 비교한다. 도구 효과만 깨끗하게 보인다. 하지만 1절의 근거로 보면 차이가 작을 수 있다.
- **나. 글자 뽑기 + 자르는 법 (선택, 사용자 결정 2026-11-16)**: 제목·표 구조를 남기는 도구로 뽑고, 소제목 단위로 자른다. 바뀌는 것이 둘이라 단계를 나눠 잰다. 먼저 같은 자르기로 도구를 비교하고, 그다음 소제목 자르기를 잰다.
- (참고) Fable 분할: 같은 일(주제 단위로 자르기)을 AI가 한다. 채팅에서 손으로 하는 방식이라 계획 1-5(적재 코드로 앞으로의 모델도 같은 방식)와 부딪힐 수 있다. 다음 대화에서 정한다.

- 마크다운 기호를 지운다: 제목 `#`, 굵게·기울임 기호, 표 칸 `|`, 구분줄, 이미지 표시, HTML 주석
- 표는 행마다 한 줄로 쓰고, 칸 사이는 공백 한 칸으로 둔다.
- 제목 글자는 지우지 않는다(기호만 지움).
- 제목 위치는 2단계를 위해 따로 보관한다.

**쪽 표시 지우기** (채팅 Claude 기본값, v1.6 셈법과 같은 정의)
- 각 쪽 글의 앞 20자 안에서, 자기 쪽 번호 N이 앞뒤에 숫자 없이 처음 나오는 자리를 찾는다.
- 삼성은 붙은 "한국어"까지 함께 본다("한국어 N" / "N 한국어").
- 그 자리와 바로 뒤의 공백 또는 줄바꿈 하나를 지운다.
- 다른 도구의 출력에는 마크다운 기호를 지운 **뒤에** 같은 규칙을 쓴다. 쪽 번호를 쪽 끝에 두는 도구가 있으므로 쪽 글의 **끝 20자**도 같은 방법으로 본다(검토 반영).
- 확인 방법:
  - 지운 글자 목록 전체를 보고한다.
  - v1.6 셈법으로 다시 셌을 때 설명서 조각의 쪽 표시가 0개여야 한다.
  - 지운 자리 밖의 글자는 그대로여야 한다(차이 비교).
  - 도구마다 쪽 글 전체에서 남은 쪽 표시를 센다. 남은 쪽 표시는 "자기 쪽 번호만 있는 줄"과 "한국어 N"·"N 한국어"다. 남은 것이 있으면 그 도구의 1단계 결과 옆에 수를 적고 한계로 남긴다. 도구가 쪽 번호를 아예 버렸으면 지울 것이 없는 것으로 본다.

**고르기**
- 2단계에 쓸 도구: "제목을 잡는 도구" 중 개발용 P 세트 5위 안 적중이 가장 높은 도구
- 차이가 1문장 이내면 설치·실행이 단순하고 빠른 쪽을 고른다.
- 제목을 잡는 도구가 없으면 2단계는 하지 않고 이유를 기록한다.

### 2단계: 소제목 단위로 자르기 (검색만)

**자르는 규칙** (채팅 Claude 기본값, 숫자는 계획에서 고정하고 개발용 결과를 보고 바꾸지 않음)
- 1단계에서 고른 도구가 잡은 제목마다 새 조각을 시작한다.
- 쪽이 바뀌어도 새 조각을 시작한다(쪽을 넘지 않음).
- 한 절이 800자를 넘으면 지금처럼 800자로 자르고 100자를 겹친다.
- 100자보다 짧은 절은 같은 쪽의 다음 절과 합친다.
- 글을 덧붙이지 않는다. 제목을 되풀이하거나 요약을 넣지 않는다. 조각 앞 제목 붙이기는 M1에서 이미 시험했다.
- 마크다운 기호 지우기와 쪽 표시 지우기는 1단계와 같다.

**최종 후보 고르기** (채팅 Claude 기본값, 검토 반영)
- 대상은 두 가지다.
  - 1단계의 도구별 실험 조각 중 개발용 P 세트 적중이 가장 높은 것(800자). 제목을 잡는지는 따지지 않는다. 목표 1("검색 결과로 고른다")에 맞추기 위해서다.
  - 2단계 소제목 자르기 실험 조각
- 7절 B-1을 통과한 것 중 개발용 P 세트 적중이 더 높은 쪽을 고른다. 차이가 1문장 이내면 800자 쪽을 고른다.
- 제목을 잡는 도구가 없어 2단계를 하지 않았으면 1단계 실험 조각만 본다.
- 하나도 통과하지 못하면 도구·자르기는 미채택으로 기록하고 3단계부터 빠진다.

### 3단계: 답변까지 (개발용 21문장)

- 대상: 운영 그대로, 쪽 표시만 지운 것, (있으면) 최종 후보
- `measure/stage2.py --blind`처럼 방법 이름을 가린 판정지로 사용자가 판정한다. 대응표 해시를 판정 전에 커밋한다(평가 규칙).
- 경계 판정은 표시하고, 뒤집었을 때 결론이 바뀌는지 리포트에 적는다.
- 5C 확인: "물이 안 빠지고 5C가 떠요"
  - 모델 washer-samsung-wd90h25, 앞 대화 없음
  - 질문 바꾸기를 포함한 서비스 흐름으로 검색부터 시작한다.
  - 쪽 표시만 지운 것과 최종 후보에서 각 3회 돌린다.

### 4단계: 확인용 세트 (한 번만)

**여는 조건** (사용자 결정): 도구·자르기의 최종 후보가 3단계(B-2)를 통과했을 때만 연다. 그렇지 않으면 4단계 대신 "운영 그대로"와 "쪽 표시만 지운 것"으로 1차 30문항과 이어지는 질문 31턴만 돌려, 쪽 표시 지우기의 회귀를 본다(7절 A-3). 확인용 세트는 봉인한 채 둔다.

**준비** (방법이 모두 굳은 뒤, 4단계 직전에만)
1. 새 응답자 3명의 확인용 10카드 문장을 정리한다. 중복, 동의하지 않은 응답, 개인정보 처리는 지난 계획 Task 1 Step 1 규칙을 따른다.
2. 카드의 11/10 기대 근거를 붙인다.
3. 카드와 다른 것을 묻는 문장은 채팅 Claude가 원문으로 확인한다.
   - 답이 설명서에 없으면 함정으로 둔다.
   - 답이 다른 쪽에 있으면 제외 후보로 올린다.
   - 최종 결정은 사용자가 한다.
4. 봉인된 지난 20문장의 해시가 `evaluation/paraphrase_split.json`과 같은지 확인한다.
5. 새 문장과 지난 20문장을 합치고 새 해시를 커밋한다.

**실행**
- 대상: 확인용 세트 + 1차 30문항 + 이어지는 질문 31턴
- 3단계와 같은 실험 조각, 같은 판정 방식으로 각 1회 돌린다.

### 운영 반영 (통과한 것이 있을 때만, 별도 계획)

- 적재 코드를 채택한 방법으로 바꾼다.
- 운영 `chunks`를 다시 넣는다. DB 작업 전에 사용자 확인을 받는다.
- 운영에서 5C를 확인한다.
- 조각 번호가 바뀔 때의 영향은 이 계획에서 정한다: 평가 세트의 `chunk:<번호>`, 실험 표, 브라우저에 저장된 대화가 조각 번호를 쓰는지.

## 7. 채택 기준 (측정 전 확정, 결과를 본 뒤 바꾸지 않음)

- "N문장 넘게 떨어지지 않음"은 같은 실행 안의 비교 대상과 견준다.
- 검색 적중은 함정을 빼고, 사람 판정 정답은 함정을 포함한 전체로 센다(결정기록 029와 같음).
- %p는 분모에 맞춰 문장 수로 바꾸고 올림한다.

### A. 쪽 표시 지우기: 나빠지지 않으면 채택 (비교 대상: 운영 그대로)

- A-1 (1단계, 사용자 결정)
  - 30문항 5위 안이 운영보다 1문항 넘게 떨어지지 않음
  - 개발용 P 세트 5위 안이 운영보다 1문장 넘게 떨어지지 않음
- A-2 (3단계, 사용자 결정): 5C 확인 3회 모두 찾음
- A-3 (회귀, 사용자 결정 2026-11-16)
  - 3단계 개발용 사람 판정 정답이 운영보다 1문장 넘게 떨어지지 않음, 환각 0
  - 1차 30문항 사람 판정이 운영보다 2문항 넘게 떨어지지 않음, 환각 0
  - 이어지는 질문 정답이 운영보다 1턴 넘게 떨어지지 않음, 환각 0
  - 4단계를 여는 경우에만: 확인용 5위 안과 사람 판정 정답이 각각 운영보다 1문장 넘게 떨어지지 않음, 환각 0
  - 4단계를 열지 않는 경우: 30문항과 이어지는 질문은 6절 4단계의 "여는 조건"에 적은 실행으로 잰다.

### B. 도구·자르기: 올라야 채택 (비교 대상: 쪽 표시만 지운 것, 계획 1-4의 숫자)

- B-1 (1·2단계, 검색만)
  - 개발용 P 세트 5위 안이 15%p 이상 오름(20문장 중 3문장 이상)
  - 30문항 5위 안이 1문항 넘게 떨어지지 않음
- B-2 (3단계)
  - 개발용 사람 판정 정답이 10%p 이상 오름(21문장 중 3문장 이상), 환각 0
  - 질문당 비용이 1.5배 이하
  - 같은 실행 안 응답 시간 증가가 0.5초 이하
- B-3 (4단계)
  - 확인용 5위 안이 10%p 이상 오르고, 사람 판정 정답이 더 많음, 환각 0
  - 30문항 사람 판정이 2문항 넘게 떨어지지 않음, 환각 0
  - 이어지는 질문 정답이 1턴 넘게 떨어지지 않음, 환각 0
  - 비용·시간은 B-2와 같음
- 계획 1-4는 30문항(27/30)과 이어지는 질문(17/18)을 고정 숫자로 견줬다. 이번에는 같은 실행 안의 비교 대상과 견준다. 허용 폭(2문항, 1턴)은 같다(채팅 Claude 해석, 결정기록 028의 "같은 실행 안 비교").

### 둘을 합쳐 정하는 법 (채팅 Claude 기본값)

- **B를 반영하려면 최종 후보도 A 기준을 운영 그대로와 견줘 모두 통과해야 한다**(A-1·A-2·A-3, 검토 반영). 그래서 최종 후보도 5C 3회를 모두 찾아야 한다. 허용 폭이 겹쳐서(A에서 1, B에서 1) 운영보다 더 많이 떨어지는 일도 막는다.
- A·B 모두 통과: B를 반영한다(B에는 쪽 표시 지우기가 들어 있다).
- A만 통과: 쪽 표시 지우기만 반영한다.
- 둘 다 통과하지 못함: 운영을 그대로 두고 미채택 결정기록을 남긴다.

- **운영 표는 건드리지 않는다.** 실험 조각은 따로 둔다.
  - `chunk_variants`가 경계와 본문이 다른 조각을 담을 수 있는지 Claude Code가 확인한다.
  - 표를 새로 만들거나 구조를 바꿔야 하면 실행 전에 사용자 확인을 받는다(CLAUDE.md).
- 3·4단계에서는 **실험 조각의 본문**이 답변 AI에 가야 한다. M2 실험처럼 운영 조각 본문을 가져오면 안 된다.
- 가이드 조각은 모든 실험 조각 한 벌에서 번호와 본문이 같아야 한다. 그래야 `chunk:<번호>` 기대 근거가 그대로 맞는다.
- 모든 실행은 `.settings.json`을 남기고, 운영 기본값과 다르면 경고한다. 실험 조각 한 벌의 이름도 설정에 적는다.
- 추출 결과와 조각 글은 git에서 뺀다. 리포트에는 위치, 글자 수, 있다/없다만 적는다.
- 채팅 Claude가 원문 대조에 쓸 파일은 git 밖 폴더에 두고, 사용자에게 읽기 권한을 받는다.
- AI 비용: 장부에 먼저 적고 `check_budget(rows, new, cap_usd=2.0)`를 통과한 뒤 실행한다. 상한 안이라도 잔액이 1달러 아래로 내려갈 실행은 하지 않는다.
- 멈출 때(v1.6과 같음): `check_budget` 실패, 실제 비용이 그 행 예상의 2배를 넘음, 원인 모를 오류 → 그 자리에서 멈추고 보고한다.
- **일정** (목표: 11/25 캠프 2차 전, 채팅 Claude 기본값)
  - 0단계 도구 하나의 설치와 첫 실행 시도는 1시간까지

  - 사람 판정은 3단계에서 최대 63건, 4단계까지 가면 최대 약 330건이다(같은 답은 묶어서 한 번만). 판정할 날짜는 계획에서 사용자와 맞춘다.

## 9. 비용 장부 (예상, 상한 2달러)

단가는 지난 장부의 실측값이다. 다시 임베딩 332행은 약 0.005달러였고, 답변 1회는 약 0.0365센트, 바꾸기 1회는 약 0.007센트다. 답변은 최대 2회(재요청)로 잡았다.

1. 0단계: 0
2. 1단계: 새로 임베딩할 실험 조각 최대 6벌 × 0.01 = 0.06 (+ 질문 임베딩 0.001 미만)
3. 2단계: 실험 조각 1~2벌 = 0.02
4. 3단계: 21문장 × 3벌 × 2회 + 5C 6회 ≈ 0.05
5. 4단계: (확인용 최대 50 + 30 + 31턴) × 3벌 × 2회 + 바꾸기 ≈ 0.25. 4단계를 열지 않으면 (30 + 31턴) × 2벌 × 2회 ≈ 0.09
6. 운영 반영: 약 0.01

합계는 약 0.39달러다.

- 쪽 단위 실행이 필요한 도구의 PDF 쪽 나누기 방법
- 마크다운 기호 지우기의 세부(표 칸 구분 기호 등). 단, 1단계 측정 전에 고정하고 모든 도구에 똑같이 적용한다.
- 실험 조각 저장 방식과 한 벌마다 붙일 이름(보고에만 적음)
- 측정 도구 확장: 실험 본문으로 답변하기, 이어지는 질문 실행
- 리포트·결정기록·개발일지 파일 이름과 번호
- 쓸 스킬: 계획 실행은 executing-plans 또는 subagent-driven-development, 코드는 test-driven-development, 병합 전 검토는 requesting-code-review, 끝났다고 말하기 전에는 verification-before-completion
