# 016. 추출 도구 선택

- 날짜: 2026-10-28
- 상태: 확정 (1일차 측정 비교) → **PDF 부분 수정 (2026-10-28 오후, 아래 "수정" 절)**
- 배경: 계획 Task 6 Step 1-2. 전처리의 `extract_pages`(PDF)와 `extract_html`(가이드 HTML)을 어떤 방식으로 구현할지 정하려고, 같은 문서로 두 방법을 나란히 비교했다. 함수 형식은 그대로이고 안쪽 구현만 달라진다.
- 비교한 것:
  - PDF: `pdfplumber` 0.11.10 vs MarkItDown 0.1.9(`markitdown[pdf]`)
  - HTML: MarkItDown vs 본문 영역만 뽑기(BeautifulSoup 4.15 + `content_selector`)
  - 비교에 쓴 스크립트는 임시 확인용이라 커밋하지 않았다. 파이썬 3.14.7에서 설치·실행을 확인했다.

## PDF 비교

| 파일 | 원본 쪽 | pdfplumber 쪽 | MarkItDown 쪽(`\f`로 나눈 개수) | 깨진 바닥글 줄 (둘 다 같음) | 본문 `(cid:…)` 잡음 줄 | 추출 글자 |
|---|---|---|---|---|---|---|
| 삼성 세탁건조기 | 80 | 80 | **1** | 79 (`UUnnttiittlleedd…`) | 123 | 약 9.4만 자 |
| LG 드럼 | 65 | 65 | **1** | 0 | 5 | 약 5.5만 자 |
| LG 벽걸이 에어컨 | 58 | 58 | **1** | 0 | 0 | 약 3.7만 자 |
| 삼성 벽걸이 에어컨 (미선정) | 57 | 57 | **1** | 57 (`RRAACC…iinndddd`) | 2 | 약 4.7만 자 |
| 삼성 일반 드럼 (미선정) | 52 | 52 | 52 | 0 | 0 | 1,148자 |

- **쪽 경계:** MarkItDown은 표처럼 보이는 쪽이 하나라도 있으면 쪽들을 `"\n\n"`로 이어 붙인다(`markitdown/converters/_pdf_converter.py`, 0.1.9). 설명서 4개 모두 1쪽으로 합쳐졌고, 이대로는 `manual:<쪽>` 근거 표기를 할 수 없다. 표처럼 보이는 쪽이 없던 삼성 일반 드럼만 다른 경로(pdfminer)로 처리되어 쪽이 나뉘었다.
- **본문 글자:** 두 도구가 같다. MarkItDown도 안에서 pdfplumber로 글자를 뽑기 때문이다. 문제 해결 쪽(삼성 `5C` 7쪽, LG 드럼 `UE` 55쪽, 두 에어컨의 고장 신고 전 확인 쪽)에서도 한 글자도 다르지 않았다.
- **깨진 바닥글:** 두 도구 모두 남긴다. 어느 쪽을 써도 `clean_text()`가 필요하다.
- **표 변환:** MarkItDown이 표로 바꾼 쪽은 오히려 나빠진다. LG 에어컨 표지는 `| 벽 걸 | 이 에 | 어컨 |`처럼 쪼개지고, 목차는 빈 칸이 많은 표가 된다. 글자 수도 10~20% 늘어난다.
- **2단 표:** "증상" 칸과 "원인" 칸이 섞이는 문제는 두 도구 모두 생긴다. 예를 들어 "냉방을 켰는데 시원하지 / 희망하는 온도가… / 않아요."처럼 나온다.

## HTML 비교 (해결 가이드 7개)

| 페이지 | MarkItDown 글자 | 본문만 글자 | MarkItDown 잡음 | 본문만 잡음 |
|---|---|---|---|---|
| LG 드럼 에러코드 (`#viewContent`) | 97,199 | 15,587 | 로그인·개인정보처리방침·사이트맵·Copyright, 링크 1,084개, 이미지 162개 | 없음 |
| 삼성 4C·5C·FC·HC·LC·oC (`div.editor-view`) | 3,490~6,530 | 197~1,867 | 전체 메뉴, 바닥글(주소·사업자 정보), 평가 설문 | 없음 |

- **숨은 탭:** LG 페이지는 탭 20개 중 19개가 숨어 있다(`is-hidden`). 문장 단위로 확인하니 두 방식 모두 숨은 탭 글을 가져왔다. 본문만 뽑기는 417/417 문장, MarkItDown은 398/400 문장이다.
- **제목·목록 구조:** MarkItDown은 `#` 제목과 목록을 남기지만, 사이트 메뉴도 같은 구조로 섞인다. 본문만 뽑기는 구조 없이 평문이다.
- **본문만 뽑기의 빈틈:**
  - 페이지 제목(`h1`)이 본문 영역 밖에 있어서 빠진다.
  - LG 탭 이름("OE [배수 문제]" 등)은 `<select>` 선택지에만 있다.
- **플렉스워시 문단:** 두 방식 모두 그대로 들어온다(oC 1곳, LC 2곳). 적용 범위로 빼는 일은 추출 뒤의 `drop_out_of_scope()`가 맡는다(결정기록 014).

## 결정

- **PDF: pdfplumber + `clean_text()`.** (→ 2026-10-28 오후 **pypdfium2로 수정**, 아래 "수정" 절) 쪽 경계를 지키는 것이 근거 표기(`manual:<쪽>`)의 전제다. 본문 글자는 같으므로 MarkItDown을 쓸 이유가 없다.
- **HTML: 본문 영역만 뽑기.** 문서별 `content_selector`는 LG `#viewContent`, 삼성 `div.editor-view`이고, `textContent` 기준이라 숨은 탭도 포함된다. 빈틈은 이렇게 메운다:
  - `extract_html(path, content_selector, title)`이 맨 앞에 `documents.json`의 `title`을 붙인다.
  - LG처럼 탭 이름이 `<select>`에만 있으면 각 탭 내용 앞에 그 이름을 붙인다.
- **MarkItDown은 쓰지 않는다.** 비교용으로 `requirements-dev.txt`에 추가했던 `markitdown[pdf]==0.1.9`는 뺀다. `requirements.txt`에는 처음부터 넣지 않았다.

## 맞바꾼 것과 다시 볼 조건

- **맞바꾼 것:**
  - 가이드의 제목·목록 구조를 잃는다. 조각 나누기와 인용에는 평문으로 충분하다고 봤다.
  - 2단 표의 칸 섞임은 두 도구 모두 못 고치므로 남는다. 평가에서 근거 적중률이 낮게 나오면 그 쪽을 다시 본다.
  - 가이드 이미지 속 글(점검 표시 이미지)은 어느 방식으로도 들어오지 않는다.
- **다시 볼 조건:**
  - MarkItDown이 쪽 경계를 지키는 옵션을 제공할 때
  - 표 구조가 답변 품질에 중요하다는 평가 결과가 나올 때
  - 사이트 구조가 바뀌어 `content_selector`가 맞지 않을 때

## 수정 (2026-10-28 오후): PDF는 pypdfium2

- **발견:** 테스트 질문의 정답을 사람이 원문으로 확인하다가(q13 이불 코스 최대 용량) 문제를 찾았다. pdfplumber가 삼성 설명서의 소수점을 지운다. "4.0 kg"이 "4 0 kg"으로 나와서, AI가 "40 kg"으로 잘못 읽을 위험이 있다.
- **첫 비교에서 놓친 이유:**
  - "소수점 유지"를 기준에 넣지 않았다.
  - MarkItDown도 안에서 pdfplumber를 쓰기 때문에, 두 도구를 비교해도 차이가 드러나지 않았다.
- **재비교:**
  - 채팅 환경에서 pdfplumber·pypdf·pdftotext·pypdfium2 4개를 비교했다. pdfplumber·pypdf는 점을 잃었고 pdftotext·pypdfium2는 유지했다(기획서 3.2).
  - Claude Code가 사용자 컴퓨터에서 pdfplumber 0.11.10과 pypdfium2 5.14.0을 같은 기준으로 다시 쟀다(아래 표). pypdf·pdftotext는 다시 재지 않았다.
  - 측정 전체 기록은 `016-부록-추출-도구-측정.md`, 재현 스크립트는 `experiments/extract_compare/`에 있다.

| 설명서 | 도구 | 쪽 | `\d\.\d ?kg` | `\d \d ?kg` | 깨진 바닥글 줄 | `(cid:` 줄 | 추출 시간 |
|---|---|---|---|---|---|---|---|
| 삼성 세탁건조기 | pdfplumber | 80/80 | 0 | **24** | 79 | 202 (바닥글 제외 123) | 6.9초 |
| | pypdfium2 | 80/80 | **24** | 0 | 0 | 0 | 0.2초 |
| LG 드럼 | pdfplumber | 65/65 | 0 | 0 | 0 | 5 | 4.4초 |
| | pypdfium2 | 65/65 | 0 | 0 | 0 | 0 | 0.2초 |
| LG 벽걸이 에어컨 | pdfplumber | 58/58 | 0 | 0 | 0 | 0 | 3.8초 |
| | pypdfium2 | 58/58 | 0 | 0 | 0 | 0 | 0.2초 |

- **삼성 38쪽:** pypdfium2는 "최대 용량: 4.0 kg", pdfplumber는 "4 0 kg"이다.
- **LG 드럼 16쪽 세제 정량 표:** pypdfium2는 "1/2 → 40 15 30", "3/4 → 50 20 35", "4/5 → 60 25 45"를 행 순서대로 뽑는다. 표 머리("세탁량 부피 / 액체세제 (ml) …")는 행 뒤에 따로 나온다. pdfplumber는 표 행 사이에 옆 칸 본문이 끼어든다.
- **바닥글 (보고 정정):** 채팅의 첫 보고는 삼성 바닥글이 "79줄 → 1줄"이었다. 이 값은 반복 글자 줄만 센 것이었다(`docs/AI-실수-기록.md` 2번). 사용자 컴퓨터에서 다시 재 보니 반복 글자 줄은 **0줄**이 됐다. 하지만 `Untitled-1 1 2026-02-26 10:06:26` 같은 바닥글이 깨지지 않은 형태로 **쪽마다 1줄씩(80줄)** 남는다. 그래서 `clean_text()`는 그대로 필요하고, 이 형태의 줄도 거르게 한다.
- **결정:** PDF 추출은 **pypdfium2**로 바꾼다(`extract_pages` 안쪽 구현만 바뀐다).
  - 로컬 전처리 전용이라 `requirements-dev.txt`에만 넣고, Vercel용 `requirements.txt`에는 넣지 않는다.
  - 비교용 pdfplumber는 Task 6에서 뺀다.
  - 회귀 방지로 Task 6 테스트에 "삼성 38쪽에 `4.0 kg`이 있고 `4 0 kg`이 없다"를 넣는다(계획 Task 6).
  - HTML 결정은 그대로다.
- **배운 것:** 비교 기준에 실제 질문에 쓰이는 값(소수점, 표의 행 순서)을 넣어야 한다. 사람이 정답을 확인하는 단계가 실제 데이터 버그를 잡았다.
