## 1차 비교 (오전) — pdfplumber vs MarkItDown 0.1.9

### PDF 4개

| 파일 | 원본 쪽 | pdfplumber 쪽 | MarkItDown 쪽(`\f`로 나눔) | 깨진 바닥글 줄(두 도구 같음) | 본문 `(cid:…)` 잡음 |
| --- | --- | --- | --- | --- | --- |
| 삼성 세탁건조기 (OID140081…) | 80 | 80 | **1** | 79 | 123줄 (18쪽 세탁 기호 표 등) |
| LG 드럼 (MFL71792818) | 65 | 65 | **1** | 0 | 5줄 (15·35쪽) |
| LG 벽걸이 에어컨 (MFL71890636) | 58 | 58 | **1** | 0 | 0 |
| 삼성 벽걸이 에어컨 (AR9500T…) | 57 | 57 | **1** | 57 | 2줄 (50쪽 아이콘) |

- **쪽 경계:** MarkItDown 0.1.9는 표처럼 보이는 쪽이 하나라도 있으면 쪽들을 빈 줄로 이어 붙인다. 4개 모두 쪽 경계 문자가 0개 → `manual:<쪽>` 근거 표기가 불가능하다.
- **본문 글자:** 문제 해결 쪽(삼성 7쪽 5C, LG 드럼 55쪽 UE, 두 에어컨의 고장 신고 전 확인 쪽)은 두 도구 결과가 한 글자도 다르지 않았다. MarkItDown도 안에서 pdfplumber를 쓰기 때문이다.
- **2단 표:** 두 도구 모두 "증상" 칸과 "원인" 칸이 섞인다(예: "냉방을 켰는데 시원하지 / 희망하는 온도가… / 않아요.").
- **MarkItDown 표 변환:** 표지·목차가 빈 칸투성이 표로 쪼개지고 글자 수가 10~20% 늘어 오히려 나빠진다.

### HTML 7개 — MarkItDown vs 본문 영역만 뽑기

본문 영역: LG `#viewContent`, 삼성 `div.editor-view`

| 페이지 | MarkItDown 글자 수 | 본문만 글자 수 | MarkItDown 잡음 | 본문만 잡음 | 제목·목록 구조 |
| --- | --- | --- | --- | --- | --- |
| LG 드럼 에러코드 | 97,199 | 15,587 | 로그인·개인정보처리방침·사이트맵·Copyright, 링크 1,084개, 이미지 162개 | 없음 | MarkItDown만 남음 |
| 삼성 4C·5C·FC·HC·LC·oC | 3,490~6,530 | 197~1,867 | 전체 메뉴, 바닥글(주소·사업자번호), 평가 설문 | 없음 | MarkItDown만 남음 |

- **숨은 탭:** LG 탭 20개 중 19개가 숨김 상태지만 두 방식 모두 숨은 탭 글을 가져왔다(본문만 417/417 문장, MarkItDown 398/400). 처음엔 MarkItDown이 7개 탭을 놓친 것처럼 보였는데 마크다운 기호 때문에 생긴 착시였다.
- **본문만 뽑기의 빈틈:** 페이지 제목(h1)이 본문 영역 밖에 있어 빠지고, LG 탭 이름("OE [배수 문제]" 등)은 `<select>` 안에만 있다 → 문서 제목과 탭 이름을 앞에 붙여 보완한다.
- **플렉스워시 문단:** oC 1문장, LC 2곳(소제목 아래 "LC1" 블록 포함) → 결정기록 014에 따라 소제목째 뺀다.

### 1차 결론

PDF는 pdfplumber + 바닥글 거르기, HTML은 본문 영역만 뽑고 제목·탭 이름 붙이기. MarkItDown은 쓰지 않는다.

## 2차 비교 (오후) — 소수점 손실 발견 후 재비교

### 발견 경위

테스트 질문 q13(삼성 이불 코스 최대 용량)의 정답을 사람이 설명서와 대조하다가, pdfplumber 추출 결과가 **"4.0 kg" → "4 0 kg"**으로 점이 빠진 것을 발견했다. 1차 비교에는 "소수점 유지" 기준이 없었고, MarkItDown도 안에서 pdfplumber를 써서 차이가 드러나지 않았다.

### 4개 도구 교차 확인 (삼성 38쪽)

| 도구 | 결과 |
| --- | --- |
| pdfplumber | `최대 용량: 4 0 kg` ❌ |
| pypdf | `최대 용량: 4 0 kg` ❌ |
| pdftotext | `최대 용량: 4.0 kg` ✅ |
| pypdfium2 | `최대 용량: 4.0 kg` ✅ |

### pdfplumber vs pypdfium2 5.14.0 (사용자 컴퓨터 재측정)

| 설명서 | 도구 | 쪽 | 소수점 유지 `\d\.\d ?kg` | 소수점 손실 `\d \d ?kg` | 반복 글자 바닥글 줄 | `(cid:` 줄 | 추출 시간 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 삼성 세탁건조기 | pdfplumber | 80/80 | 0 | **24** | 79 | 202 | 6.9초 |
| 삼성 세탁건조기 | **pypdfium2** | 80/80 | **24** | 0 | 0 | 0 | 0.2초 |
| LG 드럼 | pdfplumber | 65/65 | 0 | 0 | 0 | 5 | 4.4초 |
| LG 드럼 | **pypdfium2** | 65/65 | 0 | 0 | 0 | 0 | 0.2초 |
| LG 에어컨 | pdfplumber | 58/58 | 0 | 0 | 0 | 0 | 3.8초 |
| LG 에어컨 | **pypdfium2** | 58/58 | 0 | 0 | 0 | 0 | 0.2초 |

- 삼성 `(cid:` 202줄에는 바닥글 줄이 섞여 있다. 바닥글을 빼면 본문 잡음은 123줄로 1차와 같다.
- **남는 바닥글:** pypdfium2에서도 "Untitled-1 1 2026-02-26 10:06:26" 같은 **정상 글자 바닥글이 쪽마다 1줄(80줄)** 남는다 → `clean_text()`는 여전히 필요하지만, 깨진 글자가 없어 거르기가 쉬워진다.
- **세제 정량 표(LG 드럼 16쪽):** pypdfium2는 "1/2 → 40 15 30", "3/4 → 50 20 35", "4/5 → 60 25 45"처럼 **행 순서대로** 뽑는다(표 머리 글자는 행 뒤에 따로 나옴).
- **정정:** 채팅에서 처음 "바닥글 79줄 → 1줄"이라고 보고한 것은 반복 글자 줄만 센 값이었다. 재측정으로 위 수치로 정정했다(`docs/AI-실수-기록.md` 2번).

### 최종 결론

- **PDF:** pypdfium2 + `clean_text()`(정상 글자 바닥글 거르기). 로컬 전처리 전용이라 `requirements-dev.txt`에만 넣는다.
- **HTML:** 본문 영역만 뽑기 + 문서 제목·LG 탭 이름 붙이기.
- **MarkItDown:** 쓰지 않는다.
- **회귀 방지:** 삼성 38쪽에 "4.0 kg"이 있고 "4 0 kg"이 없는지 확인하는 테스트(Task 6), 테스트 질문 q13 핵심 단어에 "4.0"을 넣어 감시.
