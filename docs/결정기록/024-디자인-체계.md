## 사실

### 설계 값

- 색: 바탕 `#FFFFFF`, 본문 `#111111`, 면 `#F2F2F2`, 테두리 `#DADADA`, 포인트 색 없음. 시안과 설계가 다르면 설계를 따른다(기본값 11). 시안·설계의 보조 글자 `#7A7A7A`는 이번에 `#6B6B6B`로 바꾼다.

### 글꼴 부분 집합 집계

- 방법: DB `chunks` 표를 `SELECT content`로만 읽어(332개 조각, 설명서·가이드) 한글 음절(U+AC00–U+D7A3)을 세었다. 조각 본문은 어디에도 저장하지 않았다. 글꼴 cmap은 scratchpad 안 임시 가상환경의 `fonttools`와 `brotli`로 읽었다(프로젝트 의존성은 추가하지 않음).
- 조각에 나온 한글 음절은 **서로 다른 글자 851개**(전체 119,995번 나옴).
- `woff2-subset`(Regular·SemiBold·Bold 모두 같은 3,728자)에 없는 글자는 **12개, 합쳐서 13번**(전체의 약 0.011%)이다. 예(코드 포인트, 나온 횟수): U+CF06(2), U+C7AB(1), U+D526(1), U+D5D6(1), U+C9E6(1), U+D542(1), U+C62A(1), U+D49A(1), U+CEEA(1), U+CE7A(1), U+D477(1), U+D462(1). 모두 일반 낱말로 보이지 않는 글자인데, 원인(추출 잡음 여부)은 확인하지 못함.
- `woff2-dynamic-subset`(Regular 92개 파일의 cmap 합집합 12,029자)과 전체 `woff2`(14,336자)에는 빠지는 글자가 0개다.
- 한계: 조각은 설명서 쪽 글자이고, 답변은 AI가 새로 쓰므로 조각에 없는 글자가 나올 수 있다. 그런 글자는 대체 글꼴(기기 기본 한글 글꼴)로 보일 뿐 깨지지 않는다.

## 결정

1. **보조 글자색은 `#6B6B6B` 하나로 한다**(사용자 결정 12). 시안·설계의 `#7A7A7A`는 AA에 못 미쳐 바꾼다. 포인트 색은 없다.
2. **글꼴은 Pretendard 공식 배포물을 자체 호스팅한다**(기본값 6). 파일은 직접 자르지 않고 공식 것을 그대로 쓴다. `LICENSE` 원문을 글꼴 파일 옆에 함께 둔다. `font-family`는 Pretendard가 먼저, 그다음 기기 기본 한글 글꼴이다. 굵기는 400·600·700만 쓴다. 쓸 버전은 1.3.9(최신).
3. **오류·안내 색(Claude 판단 → 2026-11-10 사용자 확인: 그대로):**
   - 오류는 1차 빨강(`#B3261E` / `#FDECEA`)을 유지한다. 대비 5.72:1이고, 흑백 체계에서도 오류만은 회색과 구분되어야 한다고 봤다.
   - 개인정보 안내와 공용 가이드 경고는 1차의 갈색·노란 바탕을 지우고 면 회색 + 본문색 + 아이콘 + 굵은 라벨로 한다(16.87:1). 포인트 색이 늘지 않는다.
   - 어느 쪽이든 색만으로 구분하지 않고 아이콘과 글자 라벨을 함께 쓴다.
4. **1차 토큰 중 청록, 미색, 근거 박스 청록, 경고 색, 그림자는 지운다.**
5. **입력창 경계: A안(면 `#F2F2F2`만, 테두리 없음)으로 한다. 이유를 남긴 명시적 예외다.**(2026-11-10 사용자 결정, 앞서는 "사용자 결정 대기"였음)
   - 사실: 면 `#F2F2F2`는 흰 바탕과 1.12:1이다. W3C 이해 문서 SC 1.4.11(https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html, 2026-11-10 직접 확인)에 따르면 배경색만으로 구분하는 입력은 바탕과 3:1 이상이어야 한다(Figure 34는 이를 만족해 통과하는 예). 같은 문서는 보이는 내용(글자, 충분히 대비되는 아이콘)이 컨트롤이 있다는 것을 알려 주면 경계 표시는 필요 없다고도 한다. 입력창 안의 안내 문구를 그 "보이는 내용"으로 인정하는지는 문서에 없다(확인하지 못함).
   - 예외 이유(사용자): 누르면 키보드가 올라와 입력 위치가 바로 확인된다. 검은 보내기 버튼(18.88:1), 안내 문구(4.76:1), 화면 아래 고정 위치도 입력창이 있다는 단서다.
   - B안(회색 면 + `#8C8C8C` 테두리, 흰 바탕 3.36:1·면 3.00:1)과 C안(흰 면 + 테두리)을 비교 그림으로 보고 A안을 골랐다. `--color-border-strong`은 만들지 않는다.
   - 보완 1: 포커스 링(`--focus-ring`)은 흰 바탕·면 회색 위에서 3:1 이상이다(바깥선 `#111111` 18.88:1, 16.87:1, 가이드 대비 표). 보완 2: 계획 Task 10 Step 1 출발점에 "입력창을 바로 찾는지"를 관찰 항목으로 넣었다.
   - 타일·추천 카드·근거 박스도 면만 유지한다. 아이콘과 글자, 위치로 알아본다(같은 문서 Figure 30: 위치·글자 모양·맥락 같은 구분 단서가 있으면 대비되는 시각 표시가 필요 없음).
   - 비교 그림: `docs/design/입력창-경계-비교-2026-11-10.png`(A·C·B 세 안 비교).
   - 한계: 이 결정은 WCAG 해석을 확정한 것이 아니라 사용자가 이유를 들어 택한 예외다.
6. **부분 집합: `woff2-subset`의 Regular·SemiBold·Bold(2026-11-10 사용자 결정, 앞서는 "사용자 결정 대기"였음).** Claude의 제안을 따랐다.
   - 이유: 빠지는 글자가 12개(13번)뿐이고 빠져도 대체 글꼴(기기 기본 한글 글꼴)로 보여 읽기에 문제가 없다. 파일 3개(약 788KB)로 요청 수가 적고 단순하다.
   - 동적 부분 집합은 빠지는 글자가 없지만 파일이 276개(약 3.5MB)이고, LCP 영향은 측정하지 못했다.
   - LCP가 나쁘면 바꿀 수 있다(계획 Task 7 Step 5-1의 로컬 Lighthouse에서 먼저 본다).
7. **새 토큰 이름(Claude Code가 정함):** `--color-action`(검은 알약 버튼·보내기 동그라미 바탕), `--text-note`(13px 작은 안내), `--weight-semibold`(600, 막대·버튼·카드 제목), `--leading-ui`(1.5, 버튼·카드·말풍선 줄 간격), `--motion-slide`(250ms, 서랍·근거 펼침). 이름과 용도는 가이드 2~5절에 있다.
8. **카테고리 타일은 폭 128px 고정(`--tile-width`), 추천 카드는 글자 길이만큼 최대 272px(`--suggestion-max`), 마우스 세로 휠로 옆으로 넘긴다**(2026-11-11 사용자 결정, Task 8 화면 확인).
   - 이유: 타일(`calc(100% / 2.5)`)과 추천 카드(`calc(100% / 1.5)`)가 화면 폭 비율이라 PC(내용 폭 640px)에서 커지고 세 번째 타일이 잘렸다. 마우스 휠로는 옆으로 넘어가지 않았다.
   - 휴대폰(360px)은 지금(타일 약 131px)과 거의 같다. PC에서는 타일 3개가 다 보여 점 표시가 숨는다.
   - 긴 이름은 칸 안에서 줄을 바꾸고(단어 중간에서 끊지 않음) 같은 줄 타일 높이는 같다.
   - 휠: 가로로 넘칠 때만 세로 휠을 가로 이동(바로 이동)으로 바꾼다. 가로 휠·Shift+휠·Ctrl+휠(확대)은 브라우저 기본 동작이고, 그 방향 끝이면 화면이 위아래로 스크롤한다(휠이 갇히지 않게).
   - 비교 그림: `docs/design/타일-카드-크기-비교-2026-11-11.png`(지금·A안, PC·360px·글자가 길 때).
9. **세 번째 타일은 특정 가전 없이 흐린 "더 추가 예정"(Tabler 3.19.0 `dots` 아이콘)으로 한다**(2026-11-11 사용자 결정). 앞서는 냉장고 아이콘 + "곧 추가"였다.
   - 이유: 냉장고·전자레인지는 다루지 않는다(결정기록 003). 컴퓨터는 2차 이후이고 추가하지 않을 수도 있다(결정기록 008, 사용자).
   - `+` 아이콘은 직접 추가하는 버튼처럼 보일 수 있어 쓰지 않는다. `aria-disabled="true"`와 흐린 색은 유지한다.
   - `dots.svg`는 다른 아이콘과 같은 npm `@tabler/icons@3.19.0` 꾸러미에서 가져왔다(같은 경로의 `fridge.svg`·`LICENSE`가 저장소 파일과 같음을 2026-11-11 확인). 쓰지 않게 된 `fridge.svg`와 CSS는 지웠다.
10. **위쪽 막대 새 대화 버튼은 44px(`--tap-min`), 대화 카드 날짜는 한 줄, 파비콘 요청은 막는다**(2026-11-11 사용자 결정).
    - 새 대화 버튼: 같은 우선순위로 뒤에 적힌 `.pill`의 여백이 `.new-chat` 여백을 덮어 버튼이 48px, 막대가 56px였다. 채팅 화면 최소 높이는 막대 52px(`--tap-min` + `--space-2`)를 가정해, 대화가 짧아도 세로 스크롤이 생겼다. `.new-chat`을 `.pill` 뒤로 옮겨 44px로 맞췄다.
    - 날짜: 360px 서랍에서 "11월 / 11일"로 나뉘던 날짜를 한 덩어리(줄바꿈 없음)로 둔다. 최근 대화 카드에도 같이 적용된다.
    - 파비콘: `<link rel="icon" href="data:,">`로 `/favicon.ico` 요청(404 콘솔 오류)만 막는다. 로고 아이콘은 나중에 정한다.
11. **바탕이 `--color-surface`인 요소의 포커스 링은 회색 틈(`--focus-ring-surface`: 면 색 2px 틈 + `#111111` 2px, 안 2)으로 한다**(2026-11-11 사용자 결정, Task 8 화면 확인).
    - 적용: 입력창 알약(`.composer-box`), 카테고리 타일("더 추가 예정" 포함), 추천 카드, 모델 카드, 대화 카드(랜딩·카테고리 최근 대화, 서랍). 검은 버튼과 흰 바탕 글자 버튼·링크는 지금 `--focus-ring`(흰 틈) 그대로이고, 강제 색 모드용 `outline: 2px solid transparent`도 그대로 둔다.
    - 이유: 사용자가 입력창 포커스 링의 흰 틈이 회색 면과 "딱 맞지 않아 불편하다"고 함. 회색 틈은 틈이 보이지 않고 보내기 버튼과 선 사이 거리가 지금과 같다.
    - 안 1(틈 없는 한 줄)은 같은 날 Task 6 확인 때와 같은 이유(보내기 버튼과 선이 붙어 보임)로 다시 고르지 않았다.
    - 대비: 바깥 검정선은 그대로라 흰 바탕 18.88:1, 회색 면 16.87:1(가이드 대비 표).
    - 비교 그림: `docs/design/포커스-링-비교-2-2026-11-11.png`(지금·안 1·안 2). Task 6 확인 때의 비교는 `docs/design/포커스-링-비교-2026-11-11.png`.
    - (덧붙임 2026-11-11, 계획 3 최종 검토) 이 결정 뒤에 생긴 근거 아래 회색 알약 버튼 "공식 설명서를 드릴까요?"(`.offer`, 결정기록 021 결정 8)도 바탕이 `--color-surface`라 같은 회색 틈을 쓴다(`public/styles.css`, 가이드 6절 7).
