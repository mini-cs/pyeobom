# 펴봄 1차 회고 (2026-10-27 ~ 11-02)

> 저장 위치: `docs/회고.md` · 근거: 개발일지, 결정기록 001~020, 평가 리포트(v1·v2a·v2b), AI 실수 기록

## 한 줄 요약

RAG를 처음 직접 만들어 보면서, **측정이 계획을 바꾸고 사람의 확인이 AI의 실수를 잡는** 개발 방식을 경험했다.

## 숫자로 본 1차

| 항목 | 결과 |
| --- | --- |
| 정답률 (사람 판정, 답 있는 25개) | v1 84% → v2a **88%** |
| 환각 (함정 5개) | **0개** (v1·v2a 모두) |
| 응답 시간 (운영, 이어지는 요청 평균) | 약 7.8초 → **약 2.7초** (서버 지역 이전) |
| 비용 | 질문당 약 0.035센트 (실측 85회) |
| 기록 | PR 16개, 결정기록 20개, 테스트 150개 이상 |

## 잘한 것 (Keep)

- **RAG를 배우려고 일부러 직접 만들었다.** 문서를 글자로 바꾸고, 조각으로 나누고, 임베딩해 검색하고, 근거로만 답하게 하는 과정을 하나씩 손으로 만들어 보면서 각 단계가 무엇을 하는지 이해하게 됐다.
- **측정으로 판단했다.** 추출 도구를 같은 문서로 비교해 골랐고, 응답이 느릴 때 단계별 시간을 재서 원인(서버와 DB의 거리)을 찾았다. v1 실패를 원인별로 나눠 보니 계획했던 개선이 맞지 않아 다른 개선을 골랐다.
- **점수보다 이유를 먼저 봤다.** v2b는 자동 점수가 68% → 84%로 올랐지만, 노린 문항이 고쳐진 게 아니라서 채택하지 않았다. 같은 버전을 두 번 돌려 변동 폭(30문항 중 2개)도 먼저 쟀다.
- **AI가 만든 결과를 사람이 확인했다.** AI가 만든 테스트 정답을 원문과 대조하다가 추출 도구의 소수점 버그("4.0 kg" → "4 0 kg")를 찾았다.
- **판단을 기록으로 남겼다.** 결정기록 20개와 개발일지 덕분에, 왜 그렇게 정했는지를 나중에도 설명할 수 있다.

## 아쉬운 것 (Problem)

- **AI 도구 사용량이 생각보다 빨리 소진됐다.** 10/30~31 이틀 동안 개발을 이어 가지 못해 계획과 다르게 흘러갔다. "줄이는 순서"대로 v2b 범위를 줄이고, 사용자 테스트와 동기 따라 하기는 하지 못했다.
- **AI가 낸 숫자를 바로 믿은 적이 있다.** 바닥글 줄 수, 질문당 비용을 처음엔 그대로 받아 적었다가 다시 재서 정정했다.
- **AI의 속도를 내 이해가 따라가지 못하는 순간이 있었다.** 코드가 빠르게 늘어나면서, 내가 직접 설명할 수 있는 범위보다 결과물이 앞서 나간 부분이 생겼다.
- **사용자 검증이 부족했다.** 설문은 21명(대부분 캠프 동기)이고, 실제 사용자 테스트는 하지 못했다.

## 다음에 바꿀 것 (Try)

- **도구 사용량을 일정에 넣는다.** 큰 작업은 나눠 맡기고, 문서 작업처럼 코드가 아닌 일은 다른 도구로 나눠서 한다. 2차부터는 사용량이 넉넉한 요금제로 바꿀 예정이다.
- **AI가 쓴 코드를 내가 설명할 수 있게 공부한다.** 예를 들어 하루에 한 모듈씩 직접 읽고, "이 코드는 무엇을 왜 하는지"를 내 말로 적어 본다. 1차 코드 중 검색(`app/retrieval`)과 답변 검증부터 시작한다.
- **AI가 낸 숫자는 다른 방법으로 다시 잰다.** 비용은 토큰 수로 계산하고, 측정값은 내 환경에서 같은 스크립트로 재확인한 뒤 확정한다.
- **사용자 테스트를 일정 앞쪽에 둔다.** 2차에서는 화면을 바꾸기 전에 3명 이상에게 써 보게 하고 소요 시간을 잰다.

## AI(Claude Code)와 일하며 느낀 점

AI 없이 팀 프로젝트를 해 본 적이 있는데, 그때와 비교하면 **능률과 효율의 차이가 상당히 크다.** 하루 만에 전처리·검색·답변·API·화면·배포까지 운영 주소에 올릴 수 있었다.

다만 AI가 워낙 빠르고 잘해 나가다 보니, **내 코딩 실력보다 결과물이 앞서 나가는 느낌**을 받았다. AI를 잘 쓰려면 오히려 코드를 읽고 판단하는 힘이 더 필요하다는 걸 느꼈고, 그래서 코딩 공부를 더 해야겠다고 생각했다.

AI에게 맡기는 범위도 규칙으로 정해야 한다는 것을 배웠다. DB 구조를 바꾸거나 데이터를 지우는 일은 사람이 확인한 뒤에만 하도록 규칙을 추가했고, AI가 만든 정답과 숫자는 사람이 다시 확인하는 것을 원칙으로 삼았다.

## 2차로 가져갈 것

- 검색: 뜻은 같고 글자가 다른 질문(습기 ↔ 제습) 찾기 — 질문 확장, 쪽 제목 붙여 임베딩 등 (결정기록 020)
- 답변: 내부 용어("조각")가 답에 나오지 않게 프롬프트 다듬기, 근거를 받고도 "찾지 못함"이라 답한 문제(q16)
- 화면: 디자인 개편 후보(하단 고정 입력창, 입력창 위 예시 카드, 첫 화면 안내 2줄), 소개 영역 동작은 사용자 테스트 후 결정
- 기능: 로그인·내 가전 등록, 공식 서비스센터 연결
