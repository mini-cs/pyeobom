## 0. 한눈에 보기

- **서비스명**: 펴봄 — "설명서를 펴 보다". 공식 설명서를 대신 펴서 근거 페이지를 보여 준다는 핵심 기능에서 따왔다.
- **한 줄 정의**: 원룸 옵션 가전을 쓰는 자취생이 세탁기·에어컨 사용법이나 에러를 물으면, 그 모델의 공식 설명서에서 근거를 찾아 답해 주는 웹 서비스.
- **1차 사용자**: 원룸·오피스텔에 딸린 세탁기·에어컨을 쓰는 자취생·세입자.
- **핵심 흐름(하나만 끝까지)**: 모델 선택 → 질문 입력 → 설명서 근거 검색 → 근거가 붙은 답변(없으면 "찾지 못함").
- **기술 스택**: HTML/CSS/JS 화면 · Python(FastAPI) Vercel 함수 · OpenAI API(임베딩 + 답변) · Neon Postgres + pgvector · GitHub · Vercel 배포.
- **개발 직군 핵심 지표**: 정답률, 근거 적중률, 환각률, 응답 시간(+ 오류율). 프롬프트·검색 방식 v1 → v2 전후 비교.
- **1차 범위 원칙**: 완제품이 아니라 핵심 흐름 하나를 끝까지 + 실제 설명서로 확인 + 지표 + 문서.

## 1. 주제 선정 과정

이 주제는 처음부터 정해진 것이 아니라 AI(Claude)와의 브레인스토밍에서 기준을 바꿔 가며 좁힌 결과다. 이 과정 자체가 "AI 활용 과정"의 기록이다.

1. **첫 후보 — 개발자 업무 도구**: 에러 로그 해석기, 커밋 메시지 분류기, 결제 문자 가계부, 스미싱 판정기를 검토했다. 개발 직군 평가(정확도·응답 시간·오류율)에 맞추려고 "정답이 있는 일(분류·추출·판정)"을 기준으로 삼았다.
2. **비즈니스 모델 재검토**: "거의 모든 사람이 바이브 코딩을 하는데 이게 사업이 되나?"라는 질문에서 출발해 다시 봤다. 개발자 대상 도구는 대형 도구(예: VS Code의 Copilot 커밋 메시지 생성 기능)가 이미 기능으로 흡수했고, 사용자가 직접 만들 수 있어 돈을 낼 이유가 약했다. AI API에 프롬프트만 감싼 서비스는 누구나 따라 만들 수 있다는 "얇은 래퍼" 문제다.
3. **기준 재정의**: ① 사용자가 비개발자다, ② 쓸수록 쌓이는 데이터가 있다, ③ 정확도를 숫자로 증명하고 업무 흐름에 붙어 있다.
4. **후보 확장**: 채용공고 분석기, 예약 문의 정리기, 서술형 채점 보조, 견적서 비교기, 고지서 해석기, 영수증 정산기, 자격증 오답 분석기, 중고 매물 판정기, 그리고 **가전 설명서 Q&A**를 비교했다.
5. **선택 — 가전 설명서 Q&A**: 문서를 근거로 답하는 구조(RAG)라 "어떻게 동작하는가"를 설명할 거리가 많고, 근거가 없으면 "모른다"고 답하게 만드는 것이 곧 안정성 시연이 된다.
6. **사용자 좁히기**: 자취생·어르신·상담원을 모두 고려했지만, 사용자마다 "좋은 답"의 형식과 지표가 달라 1차는 **자취생**만 주인공으로 두고 나머지는 2~4차로 넘겼다.
7. **대상 가전**: 세탁기 + 에어컨. 컴퓨터(노트북) 수리 질문은 1차에 넣지 않고 2차 이후 카테고리 확장으로 넘겼다(근거는 3.4).

## 2. 문제 정의

### 2.1 누가, 어떤 상황에서, 왜 불편한가

- **누가**: 원룸·오피스텔에 딸린(옵션) 세탁기·에어컨을 쓰는 자취생·세입자.
- **어떤 상황에서**: 에러 코드가 떴을 때, 또는 통세척·필터 청소·예약 기능 같은 사용법이 궁금할 때.
- **왜 불편한가**:
  - **확인된 사실**: 삼성전자서비스 안내에 따르면 2012년 10월 31일 이후 판매 제품에는 책자형 설명서 대신 간단 사용설명서만 제공되고, 전체 설명서는 홈페이지에서 모델명을 입력해 내려받는 전자 매뉴얼로 제공된다. → 사용자는 모델명을 찾고, PDF를 받고, 수십 쪽을 뒤져야 한다.
  - **가설(검증 필요)**: 원룸 옵션 가전 사용자는 설명서를 갖고 있지 않은 경우가 많다 / 인터넷 검색 결과에 다른 모델 정보가 섞여 헷갈린다 / 원룸에는 여러 브랜드 가전이 섞여 있다.

### 2.2 근거 확보 계획 (1일차)

동기 대상 설문(5~10명 목표)으로 가설을 확인한다. 문항 초안:

1. 자취 중이거나 자취한 적이 있나요? 옵션 가전(세탁기·에어컨)을 써 봤나요?
2. 그 가전의 설명서를 갖고 있나요(종이/PDF/없음)?
3. 최근 가전 사용 중 막혔던 적이 있나요? 어떻게 해결했나요(검색/제조사 사이트/집주인 문의/포기)?
4. 해결까지 대략 얼마나 걸렸나요?
5. 집에 있는 세탁기·에어컨 브랜드가 서로 다른가요?

결과는 `docs/설문-결과.md`에 정리하고, 가설별로 "지지됨 / 지지되지 않음 / 판단 불가"를 표시한다.

## 3. 서비스 정의와 1차 범위

### 3.1 핵심 흐름

1. 사용자가 지원 모델 목록에서 자기 가전을 고른다. 모델명 확인 방법 안내를 함께 제공한다.
2. 질문을 입력한다. 예: "세탁 끝났는데 물이 안 빠지고 에러가 떠요".
3. 답변을 받는다. 설명서 기준 조치 방법 + **근거(설명서 이름, 페이지, 짧은 원문 인용)** + 공식 설명서 링크.
4. 설명서에서 근거를 찾지 못하면 지어내지 않고 "설명서에서 찾지 못했어요"라고 답하고, 공식 고객센터를 안내한다. 이 안내가 2차 이후 "수리 연결" 기능의 출발점이다(10.2).

**설계 판단**: 모델을 먼저 고르게 한 것은 "필터 청소"처럼 여러 가전·모델에 해당하는 질문을 가장 확실하게 구분하기 위해서다. 대신 사용자가 한 번 더 선택해야 하는 불편을 맞바꿨다.

### 3.2 대상 가전·브랜드·설명서 선정

- **세탁기**: 삼성, LG.
- **에어컨**: 삼성, LG + 캐리어·파세코·위닉스 중 약관과 설명서 제공이 확인되는 곳.
- **설명서 수**: 1차는 **총 3~4개**로 제한한다(예: 세탁기 삼성 1·LG 1, 에어컨 1~2). 나머지 브랜드는 2차 이후 추가한다.
- **선정 기준(모두 충족)**: ① 제조사 공식 사이트에서 내려받을 수 있다, ② 이용약관을 확인했다, ③ PDF에서 글자가 추출된다(에러 코드표 포함), ④ 서로 다른 브랜드·가전 조합이다.

### 3.3 1차에서 하지 않는 것과 이유

| 제외 항목 | 이유 |
| --- | --- |
| 로그인, 질문 기록 저장 | 2차(DB·로그인) 범위 |
| 어르신 모드, 상담원 화면 | 3·4차 로드맵 |
| 사진으로 모델 인식, 음성 입력 | 핵심 흐름 완성에 불필요 |
| 대화 이어 가기(이전 질문 기억) | 질문 1개 = 답변 1개로 두어야 테스트·측정이 단순함 |
| 사용자 설명서 업로드 | 파일 형식 오류·저작권 위험이 커짐. 미리 준비한 설명서만 사용 |
| 컴퓨터(노트북) 카테고리 | 3.4 참고 |

### 3.4 컴퓨터 수리를 2차 이후로 미룬 이유

- 컴퓨터 문제는 OS·프로그램·부품 등 원인이 여러 곳에 걸쳐 있어 "그 모델의 설명서 한 권"으로 답하기 어렵다.
- 테스트 30개를 세 분야로 나누면 분야당 약 10개가 되어 지표의 신뢰도가 떨어진다.
- 분해·부품 교체 안내는 안전·보증 문제가 있을 수 있다.
- 2차에 엔진은 그대로 두고 설명서만 추가하면 **"새 카테고리 추가에 걸린 시간"**을 확장성 지표로 보여 줄 수 있다. 범위는 "노트북 제조사 설명서 기반 고장 해결 안내"로 한정하고 분해 수리는 제외한다.

### 3.5 여유가 있을 때 추가할 기능 (우선순위 순)

규칙: **핵심 흐름 완성 + v2 측정이 끝난 뒤에만** 위에서부터 하나씩.

1. **같은 질문 답변 재사용(캐싱)** — 응답 시간 전후 비교 지표 추가.
2. **질문당 비용 측정** — 가상 비즈니스 모델의 비용 근거.
3. **답변 평가 버튼(👍/👎)을 Neon에 저장** — "쌓이는 데이터"의 시작, 2차 기반.
4. **답변 스트리밍** — 체감 대기 시간 감소.

## 4. 화면 디자인 방향

### 4.1 화면 구성: C안(검색형) 선택

채팅형(A), 단계형(B), 검색형(C)을 비교해 **C안**을 골랐다.

- **A(채팅형)를 고르지 않은 이유**: 1차는 대화를 기억하지 않는데, 채팅 화면은 "앞 대화를 기억한다"는 기대를 준다. 화면이 주는 기대와 실제 동작이 어긋난다.
- **B(단계형)를 고르지 않은 이유**: 질문까지 클릭 3번, 두 번째 질문부터 번거롭다.
- **C(검색형)를 고른 이유**: "질문 1개 = 답변 1개" 구조와 일치하고, 근거 카드가 눈에 띄어 "공식 설명서 근거" 차별점이 화면에 드러나며, 모바일에서 단순하다. B의 장점(모델명 찾는 법 안내)은 C의 "모델 변경" 화면에 넣는다.

**C안 화면 요소(위에서 아래로)**

0. **소개 영역(랜딩 역할, 4.2)**: 서비스명·제목·부제·신뢰 포인트 3개. 검색창을 누르면 접히면서 검색창이 위로 올라간다(동작 규칙은 4.2).
1. 선택한 모델 표시 + "변경" 링크(모델 선택 화면, 모델명 찾는 법 안내 포함)
2. 검색창("무엇이 궁금한가요?") + 남은 글자 수
3. 예시 질문 버튼(예: "통세척 방법", "에러 코드가 떴어요")
4. 답변 카드: 제목 → 조치 방법 → 근거 박스(설명서 이름·페이지·1~2문장 인용) → "공식 설명서 열기"
5. 하단 고지: "비영리 학습용 포트폴리오 · 설명서 저작권은 각 제조사"

**화면 상태**: 첫 화면(사용법 한 줄 + 예시 질문) / 로딩(진행 표시 + 버튼 잠금) / 결과 / 찾지 못함(공식 고객센터 안내) / 오류(무슨 일이 있었는지 + 다음 행동).

**기본 방향**: 모바일 우선 반응형. 자취생이 가전 앞에서 휴대폰으로 쓰는 상황을 기준으로 한다.

### 4.2 웹 제목과 첫 화면 소개 영역 (랜딩 A안)

별도 랜딩페이지(사용자용·포트폴리오용) 대신 **앱 첫 화면 위에 소개 영역**을 둔다. 들어오자마자 바로 질문할 수 있고, 1차 일정에 부담이 가장 적다. 별도 페이지는 2차 이후 필요하면 만든다(포트폴리오 소개 내용은 5일차 발표 자료·README로 먼저 만든다).

| 항목 | 문구 (확정) |
| --- | --- |
| 웹 제목(`<title>`) | 펴봄 — 가전 설명서, 대신 펴 봐 드려요 |
| 소개 제목 | 세탁기·에어컨, 설명서 대신 물어보세요 |
| 소개 부제 / 링크 미리보기 설명(`meta description`) | 공식 설명서에서 근거를 찾아 페이지와 함께 알려 드려요 |
| 신뢰 포인트 3개 | 공식 설명서 근거 · 근거 페이지 표시 · 모르면 모른다고 해요 |

**검색창 동작 규칙**

1. 검색창이나 예시 질문 버튼을 누르면 소개 영역(제목·부제·신뢰 포인트)이 약 0.3초 동안 접히고 검색창이 위로 올라간다.
2. 아무것도 입력하지 않은 채 바깥을 누르면 소개 영역이 다시 펼쳐진다.
3. 질문을 보낸 뒤에는 접힌 상태를 유지해 답변이 화면 위쪽에 보이게 한다.
4. 화면 맨 위의 서비스명 "펴봄"은 접혀도 남긴다.

- **이유**: 휴대폰에서 검색창을 누르면 키보드가 올라와 검색창·예시 질문을 가릴 수 있다. 소개 영역을 접어 입력에 집중하는 화면을 만든다.
- **접근성**: 기기에서 "동작 줄이기" 설정을 켠 사용자(`prefers-reduced-motion: reduce`)에게는 애니메이션 없이 바로 접는다.
- **맞바꾼 것**: 소개를 읽기 전에 검색창을 누르면 신뢰 포인트를 못 볼 수 있다. 빈칸으로 나가면 다시 펼쳐지므로 감수한다.
- **확인 필요**: 모바일 브라우저가 입력창을 누를 때 스스로 하는 화면 스크롤과 이 애니메이션이 겹쳐 화면이 튀지 않는지, 아이폰(Safari)·안드로이드(Chrome) 실기기에서 확인한다.

- "모르면 모른다고 해요"는 환각 방지 설계(근거 없으면 "찾지 못함")를 사용자 말로 바꾼 것이다. 화면 문구와 개발 설계가 연결된다.
- 링크를 동기들에게 공유할 때 미리보기에 제목·설명이 보이도록 `og:title`, `og:description`도 같은 문구로 넣는다.
- **이름 확인(2026-10-27)**: 웹 검색에서 같은 이름의 가전·설명서 서비스는 찾지 못했지만, 검색 결과만으로 없다고 단정할 수 없다. 특허정보검색서비스(KIPRIS) 상표 검색, Vercel 주소(`pyeobom`)·GitHub 저장소 이름 사용 가능 여부는 저장소를 만들 때 직접 확인한다.

### 4.3 레퍼런스와 디자인 가이드

- Mobbin 연결은 유료 플랜이 필요해 사용하지 않고, **직접 캡처한 레퍼런스 2~3개**를 쓴다. 대상: AI 검색 서비스의 "답변 + 출처" 화면, 제조사 고객지원 검색 페이지.
- 레퍼런스에서 배치·정보 구조·분위기 같은 **원리만** 가져온다. 로고·브랜드 고유 색 조합·고유 그림은 복제하지 않는다.
- `docs/design/디자인-가이드.md`에 색상·글꼴·글자 크기·간격·버튼/카드 모양을 **디자인 토큰**으로 정리하고, 코드에서는 CSS 변수로 쓴다.
- CLAUDE.md에 "화면 작업 시 디자인 가이드를 따른다" 규칙을 넣는다.
- 레퍼런스 원본 이미지는 공개 저장소에 올리지 않고(`.gitignore`) 출처 링크만 문서에 남긴다.
- **일정**: 1일차에 레퍼런스 선정과 가이드 확정(30분~1시간), 2일차 첫 버전부터 적용.

## 5. 시스템 구조

### 5.1 기술 스택

| 영역 | 선택 | 비고 |
| --- | --- | --- |
| 화면 | HTML / CSS / JavaScript | 바이브 코딩, 디자인 가이드 적용 |
| 서버 | Python + FastAPI, Vercel 함수 | Vercel은 FastAPI·Flask·Django 같은 파이썬 프레임워크를 지원 |
| AI | OpenAI API | 임베딩(찾기) + 답변 생성(답하기)을 키 하나로 |
| 검색 데이터 | Neon Postgres + pgvector | 모든 Neon 요금제에서 추가 비용 없이 사용 가능 |
| 전처리·평가 | Python 스크립트(로컬 실행) | PDF 처리, 테스트 자동 실행 |
| 코드·배포 | GitHub, Vercel | API 키는 Vercel 환경 변수로만 관리 |

### 5.2 구성 요소

각 부품은 한 가지 일만 하고, 따로 테스트할 수 있게 나눈다.

1. **전처리** (`ingest/`, 로컬, `python -m ingest`): PDF → 페이지별 글자 추출 → 조각 나누기 → 조각마다 브랜드·가전·모델·페이지 정보 부착 → 임베딩 → Neon 저장.
2. **검색 데이터 저장소** (Neon + pgvector): 조각 텍스트, 임베딩, 메타데이터.
3. **서버 함수** (`api/index.py` 진입 + `app/` 기능별 폴더, Vercel): 입력 검사 → 검색 → 답변 생성 → 답변 검증 → 응답.
4. **화면** (`public/`): 모델 선택, 질문 입력, 결과·상태 표시.
5. **평가** (`evaluation/`, 로컬, `python -m evaluation`): 테스트 30개 자동 실행 → 지표 계산 → 리포트.

### 5.3 질문 하나가 처리되는 흐름

1. 화면이 `POST /api/ask`로 `{ model_id, question }`을 보낸다.
2. 서버가 입력을 검사한다(빈 값, 길이, 지원 모델 여부, 개인정보 가리기 — 7장).
3. 질문을 임베딩한다.
4. **선택한 모델의 조각 중에서만** 질문과 뜻이 가장 가까운 상위 k개를 찾는다(k는 5로 시작, 평가로 조정).
5. 찾은 조각과 함께 AI에 지시한다: "이 근거로만 답하라. 근거가 없으면 찾지 못함으로 답하라. 정해진 JSON 형식으로 답하라."
6. **코드로 답변을 검증한다**: JSON 형식이 맞는가, AI가 근거로 댄 조각이 4단계에서 실제로 찾은 조각인가. 통과하지 못하면 1회 재요청, 그래도 실패하면 "찾지 못함"으로 처리한다.
7. 화면에 답변, 짧은 근거 인용과 페이지, 공식 설명서 링크, 비영리 고지를 보여 준다.

### 5.4 핵심 설계 판단 (면접 설명 포인트)

- **다른 모델 설명서가 섞이는 문제는 프롬프트가 아니라 코드(검색 필터)로 막는다.** AI에게 부탁하는 것은 어겨질 수 있지만, 해당 모델 조각만 건네주는 필터는 어겨질 수 없다.
- **환각을 코드로 한 번 더 거른다.** AI가 그럴듯한 페이지를 지어내도 실제로 찾은 조각에 없으면 통과시키지 않는다.
- **무거운 일과 가벼운 일을 나눈다.** PDF 읽기·임베딩은 미리 로컬에서, 서버는 검색·답변만 한다.
- **검색 기능을 모듈 하나로 분리한다.** 규모가 커져 전용 벡터 DB가 필요해지면 그 모듈만 교체한다.
- **1차는 인덱스 없는 정확 검색.** 조각 수가 적어(수백~천 개 추정) 전부 비교해도 충분하고 놓치는 결과가 없다. 데이터가 커지면 근사 검색 인덱스(HNSW)를 추가한다.
- **서버 함수와 DB를 같은 지역에 둔다.** Vercel 함수는 기본 지역(iad1)에서 실행되고 변경할 수 있다. 지역 맞추기 전후 응답 시간을 비교 지표로 쓸 수 있다.

### 5.5 벡터 DB 선택 (결정기록 005 요약)

| 선택지 | 판단 |
| --- | --- |
| **Neon + pgvector (선택)** | 벡터·원문·모델 정보를 한 DB에서 SQL로 다룸. 모델 필터는 `WHERE` 한 줄. 2차 로그인·기록도 같은 DB. 관리할 서비스·키가 하나 |
| 전용 벡터 DB(예: Pinecone) | 대규모에 강하고 무료 Starter 플랜이 있으나(인덱스 5개 이하, AWS us-east-1 서버리스 한정), 2차에 Neon을 어차피 써야 해 DB가 둘로 나뉨 |
| 로컬 벡터 DB(Chroma, FAISS 등) | Vercel 함수는 읽기 전용 파일 시스템 + 임시 `/tmp`(최대 500MB)만 써서 영구 저장 불가. 배포 파일에 넣으면 저작권 문제 |
| JSON 파일 + 직접 계산 | 가장 단순하지만 설명서 텍스트가 공개 저장소에 올라감. **Neon 설정이 막힐 때만 쓰는 비상안** |

결론: 1차 규모(설명서 3~4개)에서는 성능 차이보다 운영 단순성, 비용, 2차 연결, 저작권 보관이 기준이므로 Neon + pgvector를 쓴다.

### 5.6 데이터 구조 초안

```sql

  id            TEXT PRIMARY KEY,      -- 예: 'washer-brandA-modelA'
  brand         TEXT NOT NULL,
  appliance     TEXT NOT NULL,         -- 'washer' | 'aircon'

  official_url  TEXT NOT NULL,         -- 공식 다운로드 페이지

-- 검색용 조각

  id         BIGSERIAL PRIMARY KEY,
  manual_id  TEXT NOT NULL REFERENCES manuals(id),
  page       INTEGER NOT NULL,
  content    TEXT NOT NULL,
  embedding  VECTOR(<임베딩 차원>) NOT NULL   -- 사용할 OpenAI 임베딩 모델의 차원 수로 구현 시 확정
);
```

### 5.7 API 초안

**요청** `POST /api/ask`

```json
{ "model_id": "washer-brandA-modelA", "question": "물이 안 빠져요" }
```

**성공 응답**

```json
{
  "found": true,
  "answer": "조치 방법 요약…",
  "citations": [{ "manual_id": "washer-brandA-modelA", "page": 32, "quote": "1~2문장 인용" }],
  "official_url": "https://…",
  "latency_ms": 2400
}
```

**찾지 못함 응답**: `{ "found": false, "answer": "설명서에서 찾지 못했어요…", "citations": [] }`

**오류 응답**: `{ "error_code": "EMPTY_QUESTION", "message": "질문을 입력해 주세요" }` — 오류 코드 목록은 7장.

## 6. 평가 설계

### 6.1 테스트 세트 (30개)

세탁기 15~18개, 에어컨 12~15개. 유형을 섞어 쉬운 질문만으로 점수가 부풀지 않게 한다.

| 유형 | 개수(약) | 예시 | 정답 |
| --- | --- | --- | --- |
| 일반 사용법 | 12 | "통세척은 어떻게 해요?" | 설명서 해당 내용 |
| 에러 코드 | 8 | "에러 코드 ○○이 떴어요" (실제 코드는 설명서 확보 후 기입) | 설명서 에러 코드표 |
| 일상 표현 | 5 | "물이 안 빠져요", "찬바람이 안 나와요" | 설명서 해당 내용 |
| 함정: 답 없음 | 3~5 | "이 세탁기 중고 시세가 얼마예요?" | 찾지 못함 |
| 함정: 다른 모델 기능 | 2~3 | 선택 모델에는 없는 기능 질문 | 찾지 못함 |

`evaluation/questions.csv` 열: `id, model_id, question, expected_keywords, expected_page, type, expected_found`

**고정 규칙**: 테스트 세트는 1일차에 만들고 개발 중에는 바꾸지 않는다. 꼭 바꿔야 하면 `docs/평가/`에 이유를 기록한다.

### 6.2 지표 정의

| 지표 | 계산 | 비고 |
| --- | --- | --- |
| 정답률 | 맞게 답한 수 ÷ 답이 있는 질문 수 | 핵심 지표 |
| 근거 적중률 | 정답 페이지를 근거로 댄 수 ÷ 답이 있는 질문 수 | 검색 품질 |
| 환각률 | 답을 지어낸 수 ÷ 답이 없는 질문(함정) 수 | 핵심 지표 |
| 응답 시간 | 평균, 가장 느린 값 | 질문 → 답변 |
| 오류율 | 서버·형식 오류 수 ÷ 전체 요청 수 | 안정성 |

**발표의 중심 이야기 — 정답률과 환각률의 줄다리기**: "모르겠다"를 자주 말하게 하면 환각률은 내려가지만 답할 수 있는 질문까지 거절해 정답률도 내려간다. 어느 지점에서 균형을 잡았고 왜 그렇게 정했는지를 설명한다.

**임시 목표(출발점, 근거 있는 수치 아님)**: v2 정답률 80% 이상, 환각률 10% 이하. v1 측정 후 조정한다.

### 6.3 채점 방법

- **코드 자동 채점**: 근거 페이지 일치, "찾지 못함" 판정 일치, 응답 시간, 오류 여부.
- **자동 1차 + 사람 최종 확인**: 답변 내용은 `expected_keywords` 포함 여부로 1차 판정 후, 30개 전부를 사람이 훑어 최종 판정한다. AI 채점은 AI도 틀릴 수 있어 사용하지 않는다(30개 규모에서는 사람이 더 정확).

### 6.4 v1 → v2 개선 방식

1. **v1 측정**: 임베딩 검색만 + 기본 프롬프트.
2. **실패 원인 분류**:
   - **검색 실패** — 정답 조각을 아예 못 찾음. 프롬프트로는 해결 불가.
   - **답변 실패** — 맞는 조각을 찾았는데 AI가 잘못 답함. 프롬프트로 해결.
3. **한 번에 하나씩 고친다.** 예상 후보:
   - 검색: 에러 코드처럼 정확한 단어는 같은 DB의 텍스트 검색을 함께 쓴다(키워드 + 의미 결합).
   - 프롬프트: "근거 없으면 찾지 못함" 규칙 강화, 좋은 답변 예시 추가.
4. **기록**: 버전마다 무엇을 바꿨고 지표가 어떻게 변했는지 `docs/프롬프트-기록.md`, 결과표는 `docs/평가/`.

### 6.5 사용자 테스트 (보조 지표)

리뷰 그룹 동기 3~5명에게 같은 질문을 두 방법으로 해결하게 하고 시간을 잰다.

- **기존 방법**: 제조사 사이트에서 설명서를 찾아 PDF에서 답 찾기.
- **서비스**: 모델 선택 후 질문.

결과(예: "평균 X분 → Y초")는 문제 정의를 수치로 뒷받침하는 개선 전후 비교로 쓴다. 3~4일차 상호 테스트 때 진행한다.

## 7. 안정성

**원칙**: 화면에서 한 검사는 서버에서도 반드시 다시 한다(화면 검사는 개발자 도구로 건너뛸 수 있음). 1차 목표는 캠프 기준 4가지(이상 입력·실패·빈 화면·민감정보)를 **모두** 막고 시연하는 것.

### 7.1 이상한 입력

| 상황 | 처리 | 오류 코드 |
| --- | --- | --- |
| 빈 입력·공백만 | 화면: 전송 막고 안내 / 서버: 거절 | `EMPTY_QUESTION` |
| 너무 긴 입력 | 글자 수 제한(임시 500자) + 남은 글자 수 표시 / 서버도 거절 | `QUESTION_TOO_LONG` |
| 모델 미선택·지원하지 않는 모델 | 서버가 지원 모델 목록과 대조해 거절 | `INVALID_MODEL` |
| 프롬프트 인젝션("이전 지시 무시하고…") | 질문은 데이터로만 취급, JSON 형식·근거 검증을 통과한 답만 반환 | — |
| 설명서와 무관한 질문 | "찾지 못함" 처리 | — |

### 7.2 실패

| 상황 | 처리 | 오류 코드 |
| --- | --- | --- |
| OpenAI 키 누락·오류 | 요청 처리 전 확인. 사용자에겐 "일시적인 문제" 안내, 키 값은 화면·로그에 절대 남기지 않음 | `SERVICE_UNAVAILABLE` |
| OpenAI 지연·실패 | 타임아웃 설정, 1회 재시도, 실패 시 안내 | `AI_TIMEOUT` |
| Neon 연결 실패 | 안내 메시지, 원인은 서버 로그에만 | `DB_UNAVAILABLE` |
| AI 응답 형식 깨짐 | 1회 재요청, 그래도 실패 시 "찾지 못함" | — |
| 답변이 너무 김 | 최대 출력 길이 제한 | — |
| 위험한 안내(분해·전기 작업) | 지시하지 않음. 설명서가 "서비스센터 문의"라 한 작업은 그대로 안내 | — |

### 7.3 빈 화면과 로딩

- 첫 화면: 사용법 한 줄 + 예시 질문 버튼.
- 로딩: 진행 표시 + 버튼 잠금(중복 요청 방지).
- 오류·결과 없음: 무슨 일이 있었는지 + 다음 행동(예: 공식 고객센터).

### 7.4 민감정보·비용

- **개인정보 가리기**: 전화번호·이메일·주소 형식을 **OpenAI로 보내기 전에** 서버가 가린다(예: `010-****-****`) + "개인정보는 입력하지 마세요" 안내. 2차 기록 저장 시에도 가린 값만 저장.
- **비용 폭탄 방지**: OpenAI 계정에서 사용 한도를 설정할 수 있는지 확인 후 설정한다. 요청 횟수 제한은 여유 시 기능으로 둔다.
- **저작권 보호**: 8장 정책 적용.

### 7.5 시연과 기록

- `docs/안정성-테스트.md`에 "입력 → 기대 결과 → 실제 결과"를 기록한다. 3일차 상호 테스트에서 동기들이 넣은 입력도 그대로 기록.
- 입력 검사·개인정보 가리기는 자동 테스트(`tests/input_guard/`)로 만든다.
- API 실패 시연용 "실패 흉내 스위치"는 테스트 환경에만 두고 운영 배포에서는 끈다.
- **시연 영상 방어 장면 4개**: 빈 입력 차단 / 전화번호 자동 가림 / 범위 밖 질문에 "찾지 못함" / API 실패 안내.

## 9. 비즈니스 모델 (가상 시나리오)

> **포트폴리오용 가상 모델이며 실제 상용화 계획은 없다.**

- **쓰는 사람(무료)**: 1차 자취생·세입자 → 3차부터 어르신.
- **돈을 내는 고객(가상)**:
  - **1순위 — 원룸·오피스텔 관리업체, 임대인**: 세입자의 가전 문의 응대 부담을 줄인다. 건물의 가전 목록을 등록하면 세입자는 가전에 붙은 **QR코드**만 찍어 바로 질문한다(모델명을 몰라도 됨). 건물 수·세대 수 기준 월 구독.
  - **2순위 — 가전 렌탈·중고가전 업체**: 설명서 없이 제품을 받는 고객의 문의 감소.
  - **장기·가능성 낮음 — 제조사**: 이미 자체 AI 챗봇이 있음(예: 삼성전자서비스 사이트의 AI CS Bot 메뉴).
- **차별점**:
  - 제조사 챗봇은 보통 자기 브랜드만 다룬다 → 한 건물의 여러 브랜드를 한 곳에서.
  - 일반 AI는 해당 모델 공식 설명서를 근거로 답한다는 보장이 없다 → 근거 페이지 표시 + 환각률을 측정해 공개.
- **문제 해결을 끝까지**: 설명서로 스스로 해결이 안 되면 공식 서비스센터나 주변 사설 수리점으로 연결한다(2차 이후, 10.2).
- **쌓이는 데이터(복제하기 어려운 부분)**: 모델별 자주 묻는 질문, 👍/👎 평가, 실패 사례, 증상별 "자가 해결 vs 수리 필요" 통계, 실제 연결 기록에 기반한 수리점 리뷰 → 답변 품질 개선과 신뢰도의 재료.
- **가상 수익 구조**: ① 관리업체·임대인 월 구독(주 수익), ② 수리점 연결·예약 수수료(보조 수익, 4차 시나리오).
- **이해 충돌 원칙**: 수리점에서 수수료를 받더라도 **광고 노출과 리뷰 순위를 분리**하고, 광고 노출에는 광고임을 표시한다. 리뷰 순위는 돈으로 바꿀 수 없게 설계한다.

## 10. 1~4차 로드맵

> **기간은 캠프 일정으로 확정**(2026-10-27 사용자 제공). 단계별 **내용**은 1차와 "로그인·DB는 2차"만 캠프에서 확인된 것이고, 나머지는 가정이므로 각 단계 기획 때 조정한다.

### 10.0 캠프 전체 일정

| 단계 | 기간 | 발표·공유 |
| --- | --- | --- |
| 1차 | 2026-10-28(수) ~ 11-03(화), 7일 | 11-03 최종 발표 |
| 2차 | 2026-11-25(수) ~ 12-01(화), 7일 | — |
| 3차 (프로토타입) | 2026-12-18(금) ~ 12-30(수), 13일 | 2027-01-04(월) 결과 공유 및 피드백 |
| 4차 (최종) | 2027-01-05(화) ~ 01-14(목), 10일 | 2027-01-15(금) 최종 프로젝트 발표회 |
| 데모데이 | 2027-01-18(월)부터 | 데모데이 발표 |

- 기간은 달력 기준 일수다. 1·2차는 같은 수~화 패턴이라 수업일 5일로 보이고, 3·4차의 실제 수업일 수(주말·공휴일 포함 여부)는 캠프 안내로 확인한다.
- 단계 사이 기간(11/4~11/24, 12/2~12/17, 12/31~1/3)은 회고 반영, 다음 단계 기획서 작성, 약관 회신 확인 같은 준비에 쓸 수 있다.
- 4차는 데모데이까지 이어지므로, 4차 마지막에는 시연 안정성(배포 상태, 시연 시나리오, 실패 시 대체 화면)을 따로 점검한다.

### 10.1 단계별 내용 (가정)

| 단계 | 주제 | 주요 내용 |
| --- | --- | --- |
| 1차 (10/28~11/3) | 엔진 증명 | 세탁기·에어컨 설명서 3~4개, 질문 → 근거 검색 → 검증된 답변, 지표 v1 → v2 |
| 2차 (11/25~12/1) | 사용자 기능 | 로그인, 내 가전 등록, 질문 기록·👍/👎 저장(Neon), 노트북 카테고리·브랜드 추가 + "카테고리 추가 시간" 지표, **공식 서비스센터 연결(브랜드별 링크) + 수리 연결 기록 + 리뷰 기능**. 로그인 방식은 2차 기획 때 결정 |
| 3차 프로토타입 (12/18~12/30) | 가상 B2B 시나리오 + 전문가 연결 | 관리업체용 QR 페이지 프로토타입, 어르신 모드(쉬운 말·큰 글씨), **지역 기반 사설 수리점 찾기(지도·장소 검색 API, 위치 정보 처리)**, 가상 고객(페르소나) + 동기 피드백(관리업체 인터뷰는 선택). 항목이 많아 3차 기획 때 우선순위를 다시 정함 |
| 4차 최종 (1/5~1/14) | 운영 수준 | 관리업체 대시보드(자주 묻는 질문 통계), 상담원 화면, **수리 연결·예약 수수료 시나리오(가상), 리뷰 신고·숨김 관리, 증상별 "자가 해결 vs 수리 필요" 통계**, 요청 횟수 제한·모니터링·비용 최적화 |

**2차 범위 재검토 (2차 기획 때 결정)**: 2차는 1차와 같은 수업일 5일로 보이는데, 위 표의 2차 항목(로그인, 내 가전, 기록·👍/👎, 노트북 카테고리·브랜드, 공식 서비스센터 + 리뷰)은 5일에 비해 많다. 1차 회고에서 실제 작업 속도를 확인한 뒤 2차 기획서(1차와 2차 사이 기간에 작성)에서 범위를 다시 정한다. 조정 후보: 리뷰 기능을 3차(사설 수리점 찾기와 함께)로 이동 — 공식 서비스센터는 브랜드마다 하나라 리뷰를 쌓을 대상이 적다.

**관통하는 이야기**: 1차 엔진 증명 → 2차 사용자 데이터 쌓기 시작 → 3차 전문가 연결과 돈을 낼 고객 시나리오 검증 → 4차 운영 가능한 서비스로 완성.

### 10.2 수리 연결·리뷰 기능 설계 메모 (2차 이후)

**흐름**: 답변이 "찾지 못함"이거나 설명서가 "서비스센터 문의"라고 안내하는 경우 → "수리 연결" 버튼 → 공식 서비스센터(2차) / 주변 사설 수리점(3차) → 연결 기록 저장 → 일정 기간 안에 리뷰 작성 가능.

**리뷰 자격 확인 방법 비교**

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 연결 기록 기준 **(선택)** | 구현이 단순, 개인정보 부담 없음 | 실제 방문 여부는 보장 못 함 |
| 영수증 사진 인증 | 신뢰도 높음 | 영수증 속 개인정보 처리·운영 부담 |
| 작성 기간 제한(예: 연결 후 30일) **(보조로 함께 사용)** | 오래된·무관한 리뷰 감소 | 단독으로는 약함 |

**운영 위험과 원칙**

- 허위·악성 리뷰 → 신고하기 + 숨김 처리(4차).
- 이해 충돌 → 광고 노출과 리뷰 순위 분리, 광고 표시(9장).
- 위치 정보 → 정확한 위치를 저장하지 않는다. 사용자가 동네(구·동) 단위로 입력하거나 검색할 때만 쓰고 버린다.

**데이터 출처 (해당 단계 기획 때 확인)**

- 공식 서비스센터: 제조사 사이트의 센터 찾기 페이지로 연결(예: 삼성전자서비스 사이트 메뉴의 "센터찾기"). 처음에는 브랜드별 공식 페이지 링크로 시작.
- 사설 수리점: **카카오맵 API(로컬 키워드 장소 검색 + 지도 JavaScript SDK)를 1순위 후보**로 둔다.
  - 확인된 사항(카카오디벨로퍼스 문서, 2026-10-27 확인):
    - 로컬 API에 키워드로 장소 검색·카테고리로 장소 검색이 있고, 장소 상세 페이지 URL을 제공한다. 주소로 좌표 변환 API로 동네 이름을 좌표로 바꿀 수 있다.
    - 쿼터 문서에 키워드·카테고리 장소 검색이 각각 100,000건으로 표시되어 있고, 초과 시 장소 검색은 건당 2원이다(요금·쿼터는 변경될 수 있음).
    - 2026-07-21부터 무료 쿼터는 개발자 계정 기준 **첫 번째로 카카오맵 API를 활성화한 앱에만** 제공되고, 이후 앱은 비즈월렛 연결 후 사용량 과금이다. → 이전 프로젝트에서 활성화한 앱이 있는지 먼저 확인.
    - 2024-12-01부터 신규 앱은 앱 관리 페이지에서 카카오맵 사용 설정을 켜야 호출할 수 있다.
  - 사용 원칙: REST API 키는 서버 함수(Vercel 환경 변수)에만 두고, 지도 표시용 JavaScript 키는 배포 도메인을 등록해 제한한다. 검색은 "동네 + 가전 + 수리" 키워드 방식(카테고리 목록에 가전 수리가 있는지는 미확인).
  - 3차 기획 때 확인할 것: 검색 결과(장소 ID 포함)를 자체 DB에 저장할 수 있는 범위, 출처 표기 의무, 검색 기준 좌표·반경 파라미터.

**추가될 지표 후보**: 증상별 수리 연결 비율, 연결 후 리뷰 작성률.

### 11.2 기록 양식

**결정기록(ADR)** — `docs/결정기록/001-제목.md`

```markdown
# 001. 제목
- 날짜:
- 배경: 어떤 문제가 있었나
- 선택지: A / B / C (각 장단점)
- 결정: 무엇을 골랐나
- 맞바꾼 것: 무엇을 포기했나
```

**프롬프트 기록** — 버전마다: 바꾼 내용 / 바꾼 이유(어떤 실패 사례) / 지표 전후(정답률·근거 적중률·환각률·응답 시간).

**AI 실수 기록** — 건마다: Claude가 한 것 / 무엇이 틀렸나 / 어떻게 발견했나(테스트·직접 실행·문서 확인) / 어떻게 고쳤나 / 재발 방지(CLAUDE.md 규칙 추가 등).

### 11.3 CLAUDE.md에 넣을 내용

- 프로젝트 개요, 기술 스택, 폴더 구조, 실행 방법.
- **금지**: 설명서 PDF·조각 데이터·API 키·`.env` 커밋 금지.
- **작업 규칙**: 작업 후 개발일지 갱신, 중요한 결정은 결정기록 작성, 화면 작업은 디자인 가이드 준수, Vercel·OpenAI·Neon 설정은 공식 문서로 확인 후 적용, 확인하지 않은 내용을 사실처럼 쓰지 않기.

### 11.4 스킬과 작업 방식

- **직접 만들 스킬(제안)**: ① 개발일지 작성 스킬(하루 마무리 시 같은 형식으로 정리), ② 평가 실행·리포트 스킬(30개 실행 → 결과표 → 실패 원인 분류).
- **superpowers 작업 흐름**: brainstorming(이 기획서) → writing-plans(구현 계획) → 테스트 먼저 작성하는 방식의 구현 → 완료 전 검증. 이 흐름 자체를 AI 활용 과정으로 기록한다.

### 11.5 형상관리 전략 (Git·GitHub)

- **기능별 폴더**: 서버 코드는 `app/` 아래 기능 단위(core·input_guard·catalog·retrieval·answer·ask)로 나누고, 테스트도 `tests/<기능 폴더>/`로 같은 구조를 따른다. 기술 계층(models/views 등)이 아니라 기능 기준으로 나눠, 한 기능을 고칠 때 한 폴더만 보면 되게 한다.
- **기능별 브랜치**: 기능 하나 = 브랜치 하나 = PR 하나. 이름은 `<type>/<기능>`(예: `feat/input-guard`, `feat/answer`, `docs/stability-readme`). 브랜치와 Task 매핑은 구현 계획의 "브랜치 전략" 표를 따른다.
- **`main` 보호 원칙**: `main`은 항상 배포 가능한 상태로 두고 직접 커밋하지 않는다(최초 커밋 제외). 한 번에 브랜치 하나만 열고, 병합 후 최신 `main`에서 다음 브랜치를 만든다.
- **PR 절차**: 테스트 통과 → PR(양식: 무엇을·왜·테스트 결과·화면·관련 문서) → Vercel 미리보기 URL에서 확인 → merge commit으로 병합(테스트 먼저 → 구현 순서의 커밋 기록 보존) → 브랜치 삭제 → 개발일지에 PR 링크.
- **Vercel 연동**: Vercel은 브랜치 push마다 미리보기 배포를 만들고 PR에 미리보기 URL을 남기며, `main` 병합 시 운영 배포를 만든다. `FORCE_FAIL` 같은 시연용 설정은 미리보기 환경에만 둔다.
- **커밋 메시지**: `<type>(<scope>): <한국어 제목>` + 본문(무엇을·왜·테스트) + `Refs: Task 번호, 기획서 절`. type은 feat·fix·test·refactor·docs·chore, scope는 기능 폴더 이름. Claude가 커밋 전에 변경 내용을 보고 메시지를 작성해 보여 준 뒤 커밋하고, 직접 커밋할 때를 위해 `.gitmessage` 템플릿을 둔다. 코드 작업은 "실패하는 테스트 커밋 → 구현 커밋" 두 번으로 나눠 TDD 순서를 기록에 남긴다. 상세 형식과 예시는 구현 계획의 "커밋 메시지 규칙".
- **포트폴리오 효과**: PR 목록 자체가 "기능을 어떤 순서로, 어떤 근거로 만들었는가"의 기록이 된다.
