## 판단 기준 (설계 6·7절 그대로, 측정 전 확정, 결과를 본 뒤 바꾸지 않음)

**공통** (채팅 Claude 기본값)
- 숫자는 v1.9·v1.95와 같다. 응답 시간 기준과 세는 법만 다르다(B-2, 사용자 결정 +1.5초).
- 여러 회차 숫자는 두 회차를 합쳐 센다: 사람 판정 정답은 ⑰, 질문당 비용과 응답 시간은 두 회차를 합친 평균.
- 세는 법·측정 세트·⑰·덧붙임 판정 규칙(033)은 v1.9 설계 6절과 같다. 판정지 머리말에 033 규칙을 넣는다.

**0단계: 준비와 미리 보기**

1. 장부 행을 먼저 적고 `check_budget` 통과.
2. 다듬기 요청문 해시 커밋(평가 세트로 부르기 전).
3. 미리 보기: **평가 세트가 아닌 문장 20개**(계획에 적음, 채팅 Claude가 씀. 세탁기·에어컨 각 10개, 에러 코드·모델명·숫자가 든 문장과 누가 봐도 가짜인 개인정보가 든 문장 포함)를 한 번씩 다듬는다.
   - 형식: 실패·빈 문장·200자 초과 수
   - 보존 자동 검사: 질문의 에러 코드·숫자·영문 모델명이 다듬은 문장에 모두 남았는지(가린 개인정보 자리는 뺌). 다듬기 AI가 가린 질문만 받는지는 테스트로 확인한다(계획 때 고침 2026-11-23, 채팅 Claude: 다듬기 AI는 가린 질문만 받으므로 가린 정보가 다시 나타날 수 없다)
   - 채팅 Claude 읽기(사람 판정 아님): 답·원인·해결을 덧붙였는지, 없는 사실을 만들었는지
   - 시간: 다듬기 호출 평균·최대
4. 멈춤(채팅 Claude 기본값):
   - 보존 실패나 지어낸 내용이 하나라도 있으면 멈추고 사용자가 정한다(요청문을 한 번 고쳐 0단계를 다시 / 미완료). 평가 정보를 보지 않은 상태의 확인이라 결과에 맞춘 조정이 아니다.
   - **다듬기 평균이 1.5초를 넘으면** 멈추고 보고한다. 사용자가 정한다(그대로 1단계로 / "미완료(시간 예상 초과)"로 끝냄). 이 멈춤은 B-2 기준을 바꾸지 않는다.
5. 꺼짐 확인: 설정을 끈 운영 벌의 1~20위가 038 1단계 운영 결과와 같은지 대조(다르면 멈춤).

**1단계: 검색만 (한 실행 안에서 운영·후보)**

- 개발용 P 20문장과 30문항 25문장을 문장마다 **한 번만** 다듬는다(다시 돌리지 않음). 다듬기가 실패한 문장은 운영과 같은 검색이 되고, 그 수를 기록한다.
- **B-1**: 개발용 P 5위 안이 운영보다 3문장 이상 많음(20문장 중) **그리고** 30문항 5위 안이 운영보다 1문항 넘게 떨어지지 않음.
- 기록용: 순위 구간과 문장별 순위 변화, 다듬은 문장 전부(개발용·30문항은 저장소에 둬도 된다), 029 M3·v1.9 large·v1.95와 나란히 적기.
- 통과하지 못하면 미채택으로 기록하고 끝낸다. 확인용 세트는 봉인을 유지한다.

**3단계: 답변까지 (개발용 21문장, 운영과 후보 각 2회, 한 실행 안)**

- 다듬기는 회차마다 실제로 다시 한다(운영과 같은 동작).
- 판정: 사용자가 전부, 방법 이름을 가린 판정지로. 대응표 해시를 판정 전에 커밋. 033, ⑰.
- **B-2**:
  - 사람 판정 정답이 운영보다 3문장 이상 많음(21문장 중), 환각 0
  - 질문당 비용이 운영의 1.5배 이하(두 회차 합친 평균)
  - **응답 시간(사용자 결정 2026-11-23: +1.5초 이하)**: 같은 실행에서 **전체 답의 응답 시간(`latency_ms`) 평균 차이(후보 − 운영)가 +1,500ms 이하**, 두 회차를 합쳐 평균(채팅 Claude 기본값). 이유: 이 방법은 첫 질문마다 호출을 하나 더하므로, 모든 답에서 사용자가 느끼는 시간을 봐야 한다. v1.95의 "두 벌 모두 찾은 답끼리" 세기는 기록용으로만 적는다.
  - 5C 확인 3회 모두 찾음(v1.9와 같은 정의). 다듬기가 "5C"를 지우지 않는지도 함께 본다.
- 기록용: 다듬기 시간 평균, 실패(되돌림) 수, 다듬은 문장.
- 통과하지 못하면 미채택으로 기록하고 끝낸다. 확인용 세트는 봉인을 유지한다.

**4단계: 확인용 세트 (3단계를 통과했을 때만 연다)**

- 구성·준비·판정 방법은 v1.9 설계 6절 4단계와 같다(확인용은 사용자가 전부, 회귀는 ⑳).
- 이어지는 질문 31턴은 첫 턴만 다듬어진다(뒤 턴은 지금 바꾸기 그대로).
- **B-3**: v1.9 설계 6절 B-3과 같다. 응답 시간은 위 B-2의 세는 법을 쓴다.
- **반영 전에 4단계는 꼭 한다**(채팅 Claude 기본값, v1.7부터의 규칙과 같음). 개발용이 20·21문장이라 +3은 우연일 수 있어, 처음 보는 문장에서 확인해야 한다.

**결론**

- B-1·B-2·B-3을 모두 통과하면 **채택** → 8절 운영 반영. 하나라도 통과하지 못하면 **미채택**. 결정기록을 남긴다.

## 덧붙임(2026-11-23, 측정 전, 사용자 결정)

v1.96 Task 1·2 최종 검토 처리 때 정함. 측정(0단계)을 시작하기 전이고, 위 글은 고치지 않았다.

1. B-2 질문당 비용: 3단계 결과에 오류 행(`error` 칸이 비지 않은 행)이 있으면 "질문당 비용 비율(후보 ÷ 운영)"과 "오류 행을 뺀 질문당 비용 비율"이 **모두 1.5배 이하**일 때만 통과한다. 오류 행이 없으면 지금 셈 그대로다(`measure.refine_eval.stage3_report`의 `cost_pass`). 이유: 오류 행은 비용이 0으로 평균에 들어가 후보 쪽 오류가 많을수록 비율이 유리하게 낮아진다(최종 검토 M5)
2. 임베딩 비용 제외: 질문당 비용은 v1.9와 같이 답변 + 다듬기 토큰만 센다. 첫 질문 다듬기는 질문 두 개를 임베딩해 질문당 약 1e-6달러 더 들지만 뺀다(1.5배 판정에 주는 영향 약 0.003, 채팅 Claude 어림, 최종 검토 M7)
3. 0단계 형식 수는 다듬기 이유 값으로 센다: `empty`(빈 문장) · `too_long`(200자 초과) · `not_json`(JSON 아님·형식 오류) · `timeout` · `api_error`(설계 6절 0단계 3 "실패·빈 문장·200자 초과 수", 최종 검토 M6)
