# Fable 분할 실험 + MinerU 기본 층 측정 리포트

- 설계 `docs/superpowers/specs/2026-11-19-fable-split-design.md`, 계획 `docs/superpowers/plans/2026-11-20-fable-split-plan.md`, 결정기록 033
- 이름: Fable 줄 번호 분할(코드 `fable_lines`), Fable PDF 분할(코드 `fable_pdf`), MinerU 800자(코드 `mineru_800`)
- 설명서 글, 줄 번호 파일, Fable 답 원문, 조각 글은 `measure/out/fable/`(git 밖)에만 둔다. 이 리포트에는 위치·수·있다/없다만 적는다.

## 판단 기준 (설계 6절 그대로, 측정 전 확정, 결과를 본 뒤 바꾸지 않음)

**공통**
- 비교 기준점: 지금 운영(`chunks`, 측정 코드의 `None` = production)
- 후보: Fable 줄 번호 분할, Fable PDF 분할, (거르기를 통과하면) MinerU 800자
- 기록용(판정에 쓰지 않음): Docling 소제목(`docling_sections`), `strip_800`
- 세는 법은 v1.7 설계 7절과 같다: 검색 적중은 함정을 빼고, 사람 판정 정답은 함정을 포함한 전체로 센다. %p는 문장 수로 바꾸고 올림한다.
- 측정 세트: 개발용 P 21문장(검색 20), 1차 30문항(검색 25), 이어지는 질문 31턴, 확인용 세트(4단계만)

**Fable 채팅 조건** (사용자 결정 2026-11-20, 측정 전 고정, 결정기록 033)
- 추론 강도 "높음", 메모리 끔, 웹 검색 끔, 프로젝트 밖 새 채팅. 6번 모두 같은 조건
- 대화마다 추론 강도·메모리·웹 검색·채팅 종류를 화면에 보인 그대로 기록하고, 하나라도 다르면 멈추고 보고한다
- 한계: 설계 11절의 "메모리를 끄지 못한 경우"는 해당 없음(메모리 끔)

**탈락** (0단계)
- Fable 줄 번호 분할: 설명서 하나라도 받은 위치 중 버린 것(없는 쪽·줄, 형식 어긋남)이 10%를 넘으면 탈락(설계 5-2의 4)
- Fable PDF 분할: 설명서 하나라도 못 찾은 자리(형식 어긋남 포함)가 받은 자리의 10%를 넘으면 탈락(설계 5-3의 4)
- 읽을 수 있는 항목이 하나도 없으면 탈락이 아니라 "답 전체를 읽을 수 없음"으로 다시 돌리기 대상(설계 5-1의 5)
- MinerU: v1.7 0단계 거르기 탈락 조건 1~6(조건 2는 ⑫ 새 정의), 제목 잡기 비율은 기록만(설계 5-4의 3)

**B-1 (1단계, 검색만)**: 개발용 P 5위 안이 운영보다 3문장 이상 많음(20문장 중) **그리고** 30문항 5위 안이 운영보다 1문항 넘게 떨어지지 않음

**최종 후보**: B-1을 통과한 것 중 개발용 P 5위 안이 가장 높은 값을 찾고, 그 값에서 1문장 이내인 후보 중 Fable 줄 번호 분할 → Fable PDF 분할 → MinerU 800자 순으로 고른다. 통과한 것이 없으면 미채택, 확인용 세트는 봉인 유지

**B-2 (3단계, 답변까지, 개발용 21문장, 운영과 최종 후보 각 2회, ⑰)**
- 사람 판정 정답이 운영보다 3문장 이상 많음(21문장 중), 환각 0
- 질문당 비용이 운영의 1.5배 이하
- 같은 실행 안 응답 시간 증가가 0.5초 이하
- 5C 확인: "물이 안 빠지고 5C가 떠요"(washer-samsung-wd90h25, 앞 대화 없음, 질문 바꾸기 포함)를 최종 후보로 3회 돌려 모두 `found` true
- 통과하지 못하면 미채택, 확인용 세트는 봉인 유지

**B-3 (4단계, 확인용 세트, 3단계 통과 때만 연다, 운영과 최종 후보를 한 실행 안에서 각 2회)**
- 확인용 5위 안이 운영보다 10%p 이상 오르고, 사람 판정 정답이 운영보다 많음, 환각 0
- 30문항 사람 판정이 운영보다 2문항 넘게 떨어지지 않음, 환각 0
- 이어지는 질문 정답이 운영보다 1턴 넘게 떨어지지 않음, 환각 0
- 질문당 비용·응답 시간은 B-2와 같음
- 확인용 기대 근거의 옛 조각 번호(`chunk:<1~297>`)는 모든 벌에서 쪽으로 바꿔 센다(결정기록 033)

**결론**: B-1·B-2·B-3을 모두 통과하면 채택(운영 반영 후보). 하나라도 통과하지 못하면 미채택

**마감** (설계 5-5)
- Fable PDF 분할과 MinerU는 2026-11-21 저녁까지 실험 조각을 만들지 못하면 "미완료"로 적고, 있는 후보로 1단계를 잰다.
- 2026-11-24까지 4단계를 끝내지 못하면 끝낸 단계까지 기록하고 "미완료"(미채택 아님)로 둔다. 4단계 전이면 확인용 세트는 봉인 유지

## 장부 (상한 1달러)

- 상한 1달러(설계 8절, 채팅 Claude 기본값). 운영용 OpenAI 잔액 1달러를 남기는 규칙이 먼저다. 1단계 전에 사용자가 OpenAI 결제 화면에서 잔액을 확인한다.
- 각 행은 실행 전에 적고 `check_budget(앞 행들, 예상, cap_usd=1.0)`을 통과한 뒤 실행한다. 호출과 결과를 이 표에 적는다.
- 단가는 v1.7 실측값(답변 1회 약 0.0365센트, 바꾸기 1회 약 0.007센트, 임베딩 1글자 2e-8달러)
- 멈출 때: `check_budget` 실패, 실제 비용이 그 행 예상의 2배 초과, 원인 모를 오류

|---|---|---|---|---|
| 0단계: 준비(줄 번호 파일, 찾기 코드, Fable 채팅, MinerU) | 0 | | 0 | |
| 1단계: 새 실험 조각 2~3벌 임베딩(벌당 약 0.0035) + 질문 임베딩 | 0.015 | | 0.015 | |
| 3단계: 21문장 × 2벌 × 2회(재요청 포함) + 5C 3회 | 0.05 | | 0.065 | |

- Fable: 실제 지출 0(MAX 요금제 사용량은 씀). API 환산(100만 토큰당 입력 8달러, 출력 40달러)은 0단계 뒤 적는다. 채팅에서는 생각 토큰이 보이지 않아 환산 비용은 실제보다 적게 나온다.

### MinerU 기본 층 다시 하기 (Task 3, 2026-11-20 10:45:01~약 11:20 KST, 상한 2시간 안, AI 호출 없음, 비용 0)

- 진단 기록: `measure/out/fable/mineru-debug.md`(git 밖). 라이브러리 소스는 고치지 않았다.
- **원인(확인함)**
  - MinerU 기본값 `ocr_mode=auto`가 세 설명서를 모두 ocr로 분류한다(문서 분류 `classify()`를 쪽 범위별로 직접 불러 확인). ocr 모드에서는 VLM이 글 블록을 옮겨 적는다.
  - FX25 **6쪽** 블록 하나에서 VLM 출력에 깨진 UTF-8(`0xed`, 자리 63, invalid continuation byte)이 나오고, 네이티브 엔진(`mineru_llama_cpp`)이 오류를 올린다. 블록 오류 격리(`isolate_block_errors`)가 꺼져 있어 실행 전체가 멈춘다.
  - 같은 입력이면 같은 자리에서 실패했다(재현 1회 + 쪽 범위 시험 15회). 6쪽만 ocr로 돌려도 실패, 5쪽만 ocr은 통과, 1~8쪽을 `ocr_mode=txt`로 돌리면 통과.
  - 기각한 가설: 동시 처리(`max_concurrency=1`에서도 실패), 4·5쪽에 걸친 블록(4~5쪽·3~6쪽 통과)
  - 확인하지 못함: 문법 제약(`root ::= .*`)이 있는데 모델 출력에 깨진 바이트가 나오는 이유(네이티브 코드 안), `classify()`가 글자가 있는 PDF를 ocr로 고른 이유
  - v1.7 MinerU(GPU) 삼성·SQ06 출력도 ocr 모드(VLM이 옮겨 적은 글)였다.
- **고치기**: 실행 옵션 `ocr_mode=txt`(계획 Task 3 Step 2의 허용 범위). 쪽을 나눠 돌리는 우회는 6쪽이 든 창이 ocr로 분류되면 같은 실패라 쓰지 않았다.
  - (덧붙임 2026-11-20) `ocr_mode=txt`는 Claude Code가 계획 Task 3 Step 2 허용 범위에서 먼저 진행했고, 사용자가 진행 중에 승인함(2026-11-20). 기본 설정(auto)은 실행 오류로, txt는 조건 5로 탈락해 어느 쪽이든 결론은 같다.
  - 실행 스크립트: `experiments/v17_extract/run_mineru.py`에 넷째 인자 `ocr_mode`만 더한 사본(`measure/out/fable/run_mineru_ocrmode.py`, git 밖)
  - (덧붙임, 사용자 결정 2026-11-20: `ocr_mode=txt`로 계속) 같은 변경(넷째 인자 `ocr_mode`, 기본 `auto`)을 `experiments/v17_extract/run_mineru.py`에 커밋했다. 실행에 쓴 사본과 줄 끝을 빼면 내용이 같다(LF 기준 SHA-256 `218d2ba0…`). 재현 명령: `MINERU_MODEL_ONNX_DEVICE=gpu python experiments/v17_extract/run_mineru.py <PDF> measure/out/v17/extract/mineru-gpu/<doc_id>.json standard txt`
- **v1.7과 방식이 다름**: v1.7 MinerU(GPU) 삼성·SQ06은 `ocr_mode=auto` → ocr 모드(VLM이 옮겨 적은 글)였고, 이번은 txt 모드(PDF 글자 층 + 레이아웃, VLM은 일부 블록만)다.
- **GPU·VLM 사용 확인**(방법: MinerU 실행 로그의 ONNX 세션 providers, llama.cpp device policy, 진행 막대의 VLM Predict 수. 실행 중 GPU 사용률은 재지 않아 실제 연산량은 확인하지 못함)
  - ONNX: 레이아웃·글자 인식 세션의 첫째 provider가 `DmlExecutionProvider`(GPU, DirectML), 글자 위치 찾기(ocr_det)는 CPU
  - VLM: llama.cpp device policy `gpu`, 엔진 로드됨. 처리한 VLM 블록 수는 삼성 21, FX25 6, SQ06 5(v1.7 ocr 모드 FX25 첫 창 1,232블록과 비교해 일부만)
